**5-1 `schedule_store.py` 주요 내용**
- 일정과 이력을 한 JSON 문서에 저장한다(`schema_version`, `store_id`, `created_at`, `updated_at`, `schedules`, `action_history`).
- 임시 파일 + `fsync` + `os.replace`로 원자적으로 저장한다. Windows `PermissionError`는 3번 다시 시도한다.
- 저장소와 표시 파일 `*.created`가 둘 다 없을 때만 초기화한다. 사라지거나 손상된 저장소는 다시 만들지 않는다(`store_missing`, `corrupt`, `schema_error`).
- 잠금: 경로별 `threading.Lock`과 `*.lock` 잠금 파일(O_EXCL, 5초 대기). 다른 프로세스의 잠금은 지우지 않는다.
- `transact(action_id, digest, mutate)`: 잠금 안에서 다시 읽기 → 같은 id·같은 해시면 `already_executed`, 같은 id·다른 해시면 `action_id_reused` → 변경 함수 실행 → 문서 검사 → 저장
- 오류 코드: `not_initialized`, `store_missing`, `corrupt`, `schema_error`, `read_denied`, `write_denied`, `write_failed`, `lock_timeout`, `lock_error`, `seed_error`, `mutation_error`
- 운영 경로 `.safemate/schedule_store.json`(환경변수 `SAFEMATE_SCHEDULE_PATH`로 바꿀 수 있음, `.gitignore`가 `.safemate/` 제외)
- 초기 일정(상대 날짜): 오늘 08:00 아침 산책(30분), 내일 14:00 시장 장보기, 내일 16:00 복지관 방문(변경 제한), 3일 뒤 10:00 병원 진료(90분, 변경 제한). 모두 인천

**5-2 `schedule_service.py` 주요 내용**

**5-3 `outing_decision.py` 확장 내용**

- 프롬프트 규칙 9~11과 예시를 추가했다.
- `read_schedule_hint`: 제목·날짜·시각만, 최대 8개

## 6. B기능 담당자에게 전달한 계약과 변경 금지 조건

    - 필수 키 14개: status, detail_code, message, route, answer, conversation_state, missing_fields, clarification, requires_user_confirmation, proposed_action, usage, tool_trace, limitations, living_evidence
    - status: ok·needs_input·llm_unavailable·llm_invalid_output·tool_error / route: living_support·needs_clarification·error

- **변경 금지**: 함수 이름·인자·반환 키, `living_evidence`, `payload.message`, `approval` 규칙, 멱등성을 바꾸지 않는다. 새 A 기능 때문에 B가 코드를 다시 만들게 하지 않는다. B 구현이나 가짜 B 기록을 만들지 않는다. 그래프의 `b_node`·B 검사 분기·B 거절 문장을 유지한다.

## 9. 5-4단계 구현 범위와 순서 (계획 원문 6·7·8·10절)
**범위**: `schedule_agent.py`(신규), `safemate_graph.py` 확장, `test_schedule.py`에 I층·그래프 테스트 추가
- 지킬 것: 5-1·5-2·5-3 코드는 결함이 없으면 고치지 않는다. `signal`·`no_signal`·`unknown`과 `llm_suggested` 규칙을 유지한다. LLM은 승인을 대신하거나 저장소를 수정하지 않는다.

**순서**
1. **`schedule_agent.py`: `run_schedule_request(request, *, store, conversation_state=None, device=None, index=None, now=None, context=None) -> dict`**
   - 일정 이해 LLM 1회(온도 0, JSON 스키마), 3단계 `call_llm`·`ollama_settings`·`parse_model_json` 재사용
   - 스키마 필드
     - operation: query·create·update·cancel·complete·other
     - query_scope: date·target·next·remaining·week·history·summary·none
     - answers_previous_question, target_ids(이번에 넘긴 id만 enum)
     - target_text·date_text·time_text·new_date_text·new_time_text·shift_text·duration_text·title·city_text·reason_text
     - shift_base: schedule·now·unknown
     - delegate_choice, other_day_ok, check_weather, multiple_requests
     - preferences: avoid_rain·avoid_heat·avoid_cold·avoid_wind
     - category_guess
     - request_mode: request·negated·conditional·question·correction
     - exclude_previous_target, corrects_field: date·time·target·none
   - 텍스트 필드는 발화에 근거가 있어야 한다(3단계 `ground_slots` 방식).
   - `request_mode`별 처리: negated는 제안 없음·초안 폐기, conditional은 실제 예보 확인 뒤에만 제안, correction은 바뀐 항목만 갱신하고 `parse_clock(inherit_from)`을 쓴다.
   - 대상 채택은 `sv.find_targets`(single만 확정, `confirm`·`multiple`이면 묻고 `llm_suggested`는 추천으로만 표시)와 `sv.choose_from_candidates`로 한다.
   - 예보: 실외(outing) 일정이고 16일 안일 때만 `od.read_weather`(캐시 없이 재조회, `fetched_at` 표시) + `sv.forecast_status`
     - 위험 신호가 있으면 `od.choose_topics`·`od.collect_evidence`로 RAG를 부른다. `[확인한 예보]`는 `od.weather_fact_lines` 형식을 쓴다.
   - 시간 선택 위임: Python이 후보(최대 3개)와 예보를 계산 → LLM이 `{"choice": C1|C2|C3|none, "reasons": [...]}` → Python이 이유가 수치와 맞는지 확인 → 실패하면 Python 규칙(`answer_source="python_fallback"`). `unknown`인 후보는 좋은 날씨 근거로 쓰지 않는다.
   - 안내 문장은 Python 틀로 만든다. 제안은 `sv.propose_*`로만 만들고 `action_id`는 여기서 1회 생성한다.
   - 반환은 그래프가 읽는 A 계약 형식: status, route(schedule·needs_clarification·error·handoff), answer, conversation_state, missing_fields, clarification, requires_user_confirmation, proposed_action, usage, tool_trace, limitations, official_guidance, decision, llm
   - 테스트용으로 이 에이전트 전용 가짜 LLM이 필요하다. 3단계 `FakeLLM`은 stage가 "understanding"이 아니면 답변 형식을 돌려준다.
2. **`safemate_graph.py` 확장** (저장소 미연결이면 지금과 똑같이 동작)
   - State: `schedule_conversation_state`, `turn_hops`(턴당 넘김 1회 상한), `active_feature`에 `"S"` 추가
   - `build_graph(..., schedule_store=None, schedule_runner=None, life_record_reader=None)`: store가 None이면 `schedule_node`를 추가하지 않는다(G1·Mermaid 유지).
   - store가 있으면 `a_node`가 `run_outing_decision_with_schedule(schedule_hint=저장소 요약, schedule_handoff=True)`를 쓴다.
     - 일정 의도 route → `schedule_node`
     - `schedule_recheck_suggested` → `schedule_node`에서 재확인(hops 0일 때). 결과가 other·negated·question이면 3단계 답변으로 끝낸다.
     - A 제안(`propose_outing_time_change`) → `sv.link_outing_proposal`로 update·ambiguous·create·refused 처리
   - `ALLOWED_ACTIONS`에 `create_schedule`·`update_schedule`·`cancel_schedule`·`complete_schedule`(source `schedule_service`, feature S)를 추가한다. `check_feature_result`에 S 분기를 추가한다.
   - 실행 함수 S = `apply_schedule_action(…, store)`. store 모드의 `a_executor` 기본값 = `apply_outing_change`
   - `approval_card` S 미리보기(일정명·전후 시각·충돌·예보), `close` 작업별 거절 문장
   - `execute`: S type이고 status가 stale·conflict·protected·not_found·invalid_action이면 실행 함수의 안내를 보여 준다(그래도 성공 아님). G12 동작은 유지한다.
   - 일정 저장 성공 뒤 `a_conversation_state` 초기화(`a_state_reset_after_schedule_change` 기록), 일정 초안을 비운다.
   - '그만·취소·처음으로'만 단독으로 말하거나 `end_consultation`이면 S 상담도 끝낸다.
3. **테스트**
   - I층: 실제 agent·그래프 + 임시 저장소 + 가상 LLM·예보로 대표 시나리오 1~10, v2 문장 8개, A 제안 연결, 대기 중 충돌, 재실행 후 유지
   - 저장소 미연결 그래프 Mermaid가 지금과 같은지 회귀 테스트
   - L층: 실제 Qwen + 명시된 가상 예보 + 임시 저장소로 "조회 → 변경 요청 → 충돌 → 대체 제안 → 승인 → JSON 수정 → 재조회 → 새 인스턴스로 재실행 확인"과 거절 시 불변을 3회 실행
     - 판정을 4가지로 보고: 그래프 성공, 모델 판단 성공, 제안 성공, 실제 저장 성공
4. 회귀(3단계 기본·XPU, 4단계, 일정 전체), `py_compile`, Pyright 0, 보고 → 커밋 승인 요청 (`feat: [5-4단계] …`)

## 11. CUDA·XPU·CPU 자동 선택과 환경 호환성
- 요구사항 원문: [docs/5단계_요구사항_및_보완조건.md](5단계_요구사항_및_보완조건.md) 3절, 계획 원문 11절, 보완 6, 승인 조건 5
- 현재 상태
  - 자동 선택은 **아직 구현하지 않음**(5-5).
  - 2단계 `configure_embedding_device(requested)`는 cuda·xpu·cpu의 `is_available`과 텐서 연산을 확인하고, 실패하면 `SafetyError("device_error")`를 낸다. `load_embeddings`·`verify_embedding_device`는 가중치·토큰 입출력·출력 장치·384차원을 확인한다.
  - 3단계 `collect_evidence`는 장치가 xpu·cuda·cpu 중 하나이거나 환경변수 `SAFEMATE_EMBED_DEVICE`가 있어야 한다. 없으면 `rag_unavailable/device` 오류를 낸다.
  - `od.ollama_status()`는 `/api/ps`의 `size_vram`을 읽는다. 현재 실측에서 `loaded: []`였고 Ollama의 GPU 실행은 확인하지 않았다.
- 실측된 환경: Intel Arc 140T XPU(MiniLM 임베딩, `--device xpu` 테스트 통과), CPU 텐서 경로. **CUDA는 미검증.**
- 지킬 것
  - 명시한 장치가 실패하면 다른 장치로 바꾸지 않는다. 자동 선택은 실패 이유를 기록한다.
  - PyTorch 장치와 Ollama 장치를 분리해 보고한다. 요청마다 환경변수를 바꾸지 않는다. A·B 장치·색인을 분리한다.
  - `pathlib`·UTF-8·KST를 쓰고 Windows 절대 경로를 넣지 않는다.
