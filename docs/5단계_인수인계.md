## 0. 프로젝트 전체 상황

**목적과 사용자**
- SafeMate: RAG와 LangGraph 기반 독거 어르신 맞춤형 AI 생활안전·생활지원 에이전트 (생성형 AI 활용 프로그래밍 기말 팀프로젝트)
- 가상 사용자: 혼자 거주하는 78세 김○○ 어르신 (실제 개인정보 없음). 아침(생필품·장보기), 낮(외출·날씨·일정), 저녁(승인한 일정·요청 확인) 시나리오
- 상용 수준의 답변 품질보다 실제 기능 구현과 안정적인 시연을 우선한다.

**기능과 역할 분담**
| 구분 | 내용 | 담당 |
|---|---|---|
| A기능 | 날씨 기반 외출 의사결정(1단계 Open-Meteo, 2단계 공식 안전수칙 RAG, 3단계 Qwen 이해·답변·검증) | 정지호 |
| 일정 관리(5단계) | 가상 일정 JSON 저장소, 자연어 조회·등록·변경·취소·완료, 날씨·RAG 종합 판단, 승인 후 영구 저장 | 정지호 |
| 공통 LangGraph(4단계)·Gradio(6단계)·최종 통합 | A·B·일정 분기, 승인·거절, 실행 | 정지호 |

## 3. 1~5-3단계 구현 내용 (보존)
**5-1 `schedule_store.py` 주요 내용**
- 일정과 이력을 한 JSON 문서에 저장한다(`schema_version`, `store_id`, `created_at`, `updated_at`, `schedules`, `action_history`).
- 임시 파일 + `fsync` + `os.replace`로 원자적으로 저장한다. Windows `PermissionError`는 3번 다시 시도한다.
- 저장소와 표시 파일 `*.created`가 둘 다 없을 때만 초기화한다. 사라지거나 손상된 저장소는 다시 만들지 않는다(`store_missing`, `corrupt`, `schema_error`).
- 잠금: 경로별 `threading.Lock`과 `*.lock` 잠금 파일(O_EXCL, 5초 대기). 다른 프로세스의 잠금은 지우지 않는다.
- `transact(action_id, digest, mutate)`: 잠금 안에서 다시 읽기 → 같은 id·같은 해시면 `already_executed`, 같은 id·다른 해시면 `action_id_reused` → 변경 함수 실행 → 문서 검사 → 저장
- 오류 코드: `not_initialized`, `store_missing`, `corrupt`, `schema_error`, `read_denied`, `write_denied`, `write_failed`, `lock_timeout`, `lock_error`, `seed_error`, `mutation_error`
- 운영 경로 `.safemate/schedule_store.json`(환경변수 `SAFEMATE_SCHEDULE_PATH`로 바꿀 수 있음, `.gitignore`가 `.safemate/` 제외). **현재까지 운영 파일은 만들어지지 않았다** (모든 테스트·실측은 임시 폴더)
- 초기 일정(상대 날짜, `data/schedule/seed_schedule.json`): 오늘 08:00 아침 산책(30분), 내일 14:00 시장 장보기(60분), 내일 16:00 복지관 방문(변경 제한), 3일 뒤 10:00 병원 진료(90분, 변경 제한). 모두 인천. id는 `schedule_001`~`004`

**5-2 `schedule_service.py` 주요 내용** (5-4·5-5에서 수정하지 않음)
- 날짜·시각: `parse_day`, `parse_clock(text, inherit_from)`, `parse_minutes`, `resolve_shift`, `normalize_numbers` (3단계 `parse_date_text`·`parse_clock_text`·`parse_lead_text` 재사용)
- 조회: `schedules_on/between`, `week_range`, `next_schedule`, `running_schedules`, `remaining_today`, `history_entries`, `display_state`(scheduled·running·overdue·completed·cancelled), `describe`, `korean_time`, `korean_day`
- 식별: `find_targets`(single·multiple·none·unspecified·confirm, `llm_suggested`), `choose_from_candidates`(부정·정정 처리), `recent_reference`, `covers_clock`(자정 넘김)
- 충돌·후보: `find_conflicts`([start, end)), `find_free_slots`(자동 추천 07~21시, 30분 간격, 최대 3개, 다른 날짜는 허락 시 최대 3일), `forecast_status`(signal·no_signal·unknown)
- 제안: `propose_update/create/cancel/complete` (공통 봉투, type `update_schedule`·`create_schedule`·`cancel_schedule`·`complete_schedule`, source `schedule_service`), `completion_check`
- 실행: `apply_schedule_action(approved, store)`
  - 잠금 안 현재 시각 기준으로 버전·변경 전 내용·충돌·보호·작업별 변경 가능 항목·소요 시간·승인 내용을 대조한다.
  - 결과: `{status, message, action_id, applied, mock, record, answer}`, status는 ok·already_executed·rejected·invalid_action·stale·conflict·protected·not_found·error
- `apply_outing_change`: 대상 확인이 안 된 옛 3단계 봉투는 거절한다.
- `link_outing_proposal(doc, a_result, now)`: kind = update·ambiguous·create·refused·invalid
- `life_record`(B 미연결이면 `not_connected`), `read_living_action_log`(명세 2.3 JSONL 읽기 전용)

### 5.2 자동 선택과 검사 단계

- `torch.version.cuda`·`xpu`는 `getattr`로 **기록만**(build). 없다고 장치를 빼지 않는다.
- auto: 모든 단계를 통과한 첫 장치 선택, 실패 시 전환 이유 기록. **수동 지정: 그 장치만 검사, 실패해도 다른 장치로 바꾸지 않음.** CPU까지 실패하면 `ok=False`("실행 가능한 임베딩 장치가 없습니다")
- 모델 로딩 실패와 임베딩 실패는 기존 `load_embeddings`가 같은 `model_error`로 감싸므로, verify의 `ValueError` 머리말("선택 장치"·"임베딩 장치·차원 불일치")이 원인인 경우만 `embedding_verify`로 나누고, 나머지는 원래 예외와 판단 한계(`AMBIGUOUS_MODEL_NOTE`)를 기록
- 캐시: 성공한 장치 모델은 `load_embeddings`의 `lru_cache`(최대 3)에 남아 RAG 색인 준비가 재사용한다. 여러 장치를 직접 검사하면 장치별로 쌓일 수 있어 `cached_models`로 보고. 실패한 장치만 `gc.collect()`·`empty_cache()`(정리 오류는 `cleanup_error`로 따로 기록)
- 전역 환경변수(`SAFEMATE_EMBED_DEVICE`, `CUDA_VISIBLE_DEVICES`)를 읽거나 바꾸지 않고, 일정 저장소를 만들거나 읽지 않는다.

### 5.3 그래프 연결 (`safemate_graph.py`)
- `build_graph(a_device="auto")`: 그래프를 만들 때 **한 번만** 선택하고, 선택한 장치 이름을 기존 `a_device` 자리에 넣어 A 외출 판단과 일정 에이전트의 RAG에 전달. 요청마다 다시 고르지 않음
- 모든 장치 실패 → `DeviceSelectionError`(그래프 생성 중단)
- 자동 선택 모드에서 주입한 `a_index`의 장치 확인(`_index_check`): 종류와 **실제 장치 번호(embedding)까지 같아야 match**, 다르면 mismatch, 실제 장치 정보가 없으면 unverified → 둘 다 `IndexDeviceError`(그래프 생성 중단). 색인은 지우거나 다시 만들지 않는다. `a_index=None`이면 lazy(첫 검색 때 선택 장치로 준비)
- **한계: 장치 번호 엄격 검사는 자동 선택 모드에만 적용.** 명시 장치·None은 기존 계약대로 3단계 `collect_evidence`의 종류 비교만 한다.
- `b_device="auto"`: B 미연결이면 고르지 않음, 연결되면 `select_torch_device`. B 색인에 A의 MiniLM 검증 규칙을 강제하지 않음
- `runtime_report(graph, *, include_ollama=False)`: 그래프별 실행 정보(`WeakKeyDictionary`)의 **사본**. a(요청·선택·색인 확인), b, schedule_store 연결 여부. 모르는 그래프는 `unknown_graph`
- 기본 인자 `a_device=None`은 그대로 유지. **6단계 최종 앱에서 auto를 기본 실행 경로로 연결해야 한다.**

### 5.4 3단계 CLI와 진단 CLI

### 5.5 Ollama 추론 장치 독립 보고
- PyTorch 장치와 Ollama 장치는 다른 시스템으로 따로 보고. GPU 종류(NVIDIA·Intel)와 추론 백엔드는 API로 확인할 수 없어 확정하지 않음
- 대상 모델(`qwen2.5:3b`, `:latest` 같은 이름)만 판정. name·model이 문자열이 아니거나 없거나 서로 다르면 `invalid_model_info`
- bool·음수·정수 아님·size 0·size_vram > size·중복 항목은 `invalid_values`. `size_vram=0` → "GPU 메모리 사용이 보고되지 않음", 양수 → 전체/부분 적재(모든 연산이 GPU라는 보장 아님)
- 3단계 `ollama_status()`가 `[]`·null 응답으로 예외를 내면 `response_error`(서버 실행·모델 설치는 '확인 못함', 미설치·CPU로 보지 않음)
- `--ollama-probe`: 짧은 실제 호출(`call_ollama`, 최대 16토큰) 전후를 따로 측정. 호출 직후에도 미적재면 '장치 측정 실패'
- `ollama ps`: SafeMate 서버가 경로 없는 `http` 주소이고 `OLLAMA_HOST`의 스킴·경로·호스트·포트가 같을 때만 실행, 종료 코드 0일 때만 PROCESSOR 칸을 참고 정보로 기록(판정에 쓰지 않음)

## 17. B기능 및 Gradio 관련 현재 결정 (사용자 결정 사항)
- B기능 담당 팀원(이석원)은 **아직 개발을 시작하지 않았다.** 팀원에게 `SafeMate_AB_Interface.md`를 전달했다.
- B기능 담당은 명세서 2장에 맞춰 `run_living_support()`, `execute_living_action()`을 구현한다. LangGraph·Gradio·공통 승인 버튼은 구현하지 않는다.
- B 인터페이스는 이미 전달했으므로 임의로 변경하지 않는다. 실제 B기능은 아직 검증되지 않았다. **B기능을 대신 개발하지 않는다.**
- 현재는 5단계에 집중한다.
- 6단계 Gradio 작업은 **사용자와 화면 및 기능 요구사항을 먼저 확정한 뒤** 시작한다. 디자인, 접근성, 화면 구성, 일정 관리 화면, 승인 카드, 출처 표시, 개발자 패널, 세션 분리 등을 임의로 확정하지 않는다.
- B기능 미완성 상태에서 A와 일정 관리 화면을 먼저 구현하는 방안은 **제안된 사항일 뿐 확정된 6단계 계획이 아니다.**
- 6단계 최종 앱에서 자동 장치 선택(`build_graph(a_device="auto")`)을 기본 실행 경로로 연결한다.
