## 0. 기본 원칙 (5단계 요청 3절)

1. 1·2단계 코드는 수정하지 않는다.
2. 3단계 코드는 일정 조회·관리와 자연어 이해에 필요한 범위에서만 수정한다.
3. 4단계 코드는 새로운 일정 관리 제안과 실행 함수를 연결하는 데 필요한 범위에서만 수정한다.
4. 기존 파일 전체를 불필요하게 다시 쓰지 않는다.
5. 기존 공개 함수와 반환 구조의 호환성을 유지한다.
6. 팀원에게 이미 전달한 B기능 인터페이스 명세서 2장의 규격을 변경하지 않는다.
7. 기존 테스트를 삭제하거나 기대값을 느슨하게 만들어 억지로 통과시키지 않는다.
8. 자연어 이해와 상황에 따른 제안은 LLM이, 날짜 계산·충돌 검사·데이터 저장처럼 정확성이 필요한 작업은 Python이 담당한다.
9. 사용자 승인 여부와 후속 실행은 LangGraph의 상태와 조건부 분기로 관리한다.
10. LLM에게 파일을 직접 수정할 권한이나 사용자 승인을 만들 권한을 주지 않는다.
- 데이터 검증을 위한 Python 조건문은 쓸 수 있다. 다만 사용자 요청 전체를 단순 키워드 매칭이나 거대한 if-else로 처리하지 않는다.

## 1. 요구사항 01~42

### A. 자연어 날짜·시간 처리
- **01 자연어 시각**: 아침 여덟 시, 오전 아홉 시 반, 낮 열두 시, 오후 두 시, 오후 네 시쯤, 저녁 일곱 시, 밤 아홉 시, 새벽 한 시, 오후 네 시 십오 분, 세 시 반, 네 시 조금 넘어서
  - 내부에서는 정확한 KST로 정규화하고, 사용자에게는 오전·오후로 안내한다.
  - 오전·오후를 확정할 수 없으면 추측하지 않는다.
- **02 자연어 날짜**: 오늘·내일·모레·글피, 이번 주 금요일, 다음 주 월요일, 이번 주말, 다음 달 3일, 12월 5일, 그날, 다음 날
  - 기준은 현재 한국 시각이고, 앞 대화에서 확정된 날짜가 있으면 문맥을 고려한다.
  - 연말·연초·월말·윤년·자정 경계와 존재하지 않는 날짜를 검증한다. 모호하면 묻는다.
- **03 상대 시간**: 지금부터 9시간 뒤, 두 시간 후, 한 시간만 미뤄 줘, 원래 시간보다 30분 앞당겨 줘, 다음 날 같은 시간, 일주일 뒤
  - 현재 시각 기준인지 기존 일정 기준인지 구분한다. 계산은 LLM이 아니라 Python `datetime`이 한다.
- **04 부족한 정보 질문**: "내일 일정 바꿔 줘", "일정 좀 미뤄 줘", "네 시에 가려고", "아무 때나 괜찮아", "다음 주에 병원 가야 해"
  - 한 번에 너무 많이 묻지 말고 필요한 항목부터 확인한다.
  - 기존 일정에서 확인할 수 있는 정보는 다시 묻지 않는다.
  - 대상이 여러 개이거나 날짜·시각을 확정할 수 없으면 선택지를 보여 주거나 묻는다.
- **05 다중 턴과 수정 반영**: 예) "내일 시장 가는 시간을 바꿔 줘" → "내일 오후 2시 예정, 몇 시로?" → "오후 네 시쯤" → "4시엔 다른 일정, 5시는?" → "아니, 모레 오전으로 해 줘"
  - 사용자가 바꾼 항목만 갱신하고 나머지는 유지한다.
  - 새 일정 요청으로 바뀌면 이전 대화의 오래된 정보가 섞이지 않게 한다.

### B. 내부 가상 일정 관리
- **06 JSON 저장소**: 외부 캘린더 연동 없음. Python 표준 라이브러리로 읽고 쓰는 내부 JSON. 가상 사용자 일정만 저장한다.
- **07 날짜별·목적별 조회**: "오늘 일정 알려 줘", "내일 뭐 하지?", "병원 가는 날이 언제지?", "시장에 몇 시에 가기로 했더라?", "이번 주에 무슨 일정이 있어?"
  - 저장된 기록만 조회하고, 없는 일정을 만들어 내지 않는다.
- **08 변경 대상 식별**: "시장 가는 거", "장보는 거", "병원 약속", "아까 바꾼 일정", "내일 오후 일정"
  - 하나면 그 일정을, 여러 개면 후보를 보여 주고 묻는다. 없는 일정을 바꿨다고 처리하지 않는다.
- **09 충돌·소요 시간**: 시작·종료 시각(소요 시간)으로 검사한다. 예) 16~17시 복지관과 16:30 시작 일정은 충돌.
  - 기존 소요 시간을 유지하며 변경할 수 있는지 확인한다. 자정을 넘는 일정도 올바르게 비교한다.
- **10 변경 제한 일정 보호**: 병원 예약 등 제한 일정은 AI가 임의로 바꾸지 않는다.
  - 다른 일정과 충돌해도 보호 일정을 대신 옮기거나 취소하지 않는다. 바꿀 수 없는 이유와 대안을 안내한다.
- **11 빈 시간·날짜 탐색**: 같은 날 다른 시간, 사용자가 허용한 다른 날짜, 소요 시간을 고려한 빈 시간대
  - 기본은 지정한 날짜 유지, 다른 날짜는 먼저 확인한다. 탐색 기간과 후보 수를 제한한다(최대 3개 정도, 무한 탐색 금지).
- **12 종료 후에도 유지**: `InMemorySaver`에만 두지 않고 JSON에 실제로 반영한다. 재실행해도 확인할 수 있어야 하며, 매번 초기 일정으로 덮어쓰지 않는다.

### C. 지능형 일정 의사결정
- **13 날씨·RAG·일정 종합 판단**: 외출 목적, 기존 일정, 변경 요청 시각, 충돌 여부, 실제 시간대별 예보, 필요한 공식 안전수칙, 변경 가능 여부
  - 실제 조회 결과에 근거한다. 단순 조회·실내 일정에는 날씨·RAG를 무조건 부르지 않는다.
- **14 일정을 기억하지 못하는 경우**: "내가 내일 뭐 하기로 했지?", "시장 몇 시에 가기로 했더라?", "아까 무슨 일정을 바꿨지?", "오늘 약속이 있었나?"
  - 기록을 조회해 확인된 내용만 알려 준다. 저장된 내용을 다시 입력하라고 하지 않는다.
- **15 시간 선택 위임**: "비 안 오는 시간으로 알아서 바꿔 줘", "아무 때나 빈 시간으로 잡아 줘", "네가 괜찮은 시간으로 추천해 줘", "다른 약속하고 안 겹치게 해 줘"
  - Python이 가능한 후보를 계산하고, LLM은 근거를 이해해 후보와 이유를 설명한다.
  - 좋은 후보가 없으면 무리하게 추천하지 않는다. 위임 발화도 최종 승인이 아니다.
- **16 날씨와 무관한 변경**: 늦잠, 친구 방문, 피곤함, 다른 약속 등 개인 사정을 고려한다. 의료 판단·건강 진단은 하지 않는다.
- **17 최신 예보 재조회**: 바꾼 일정도 요청하면 최신 예보를 조회한다. 오래된 캐시를 최신으로 오인하지 않는다.
  - 예보 변화·새 충돌이 있으면 대안을 제시한다. 기존 승인으로 새 변경을 자동 적용하지 않고 반드시 다시 승인받는다.
- **18 Qwen 의도 분류 보완**: 단순 날씨, 외출 안전 상담, 일정 조회, 일정 변경, 신규 등록, 취소, 완료 기록, 변경 이력 조회, 다음 일정 조회, 생활지원 B기능 요청을 구분한다.
  - LLM 구조화 출력과 검증된 대화 상태를 활용하고, 기존 자연어 처리 함수를 중복 구현하지 않는다.
  - 실제 LLM 성능 문제와 프로그램 결함을 구분해 보고한다.

### D. LangGraph 승인과 실행
- **19 변경 전후 안내**: 일정 이름, 기존 날짜·시간, 후보 날짜·시간, 변경 이유, 충돌 여부, 필요하면 예보와 안전수칙. 무엇을 승인하는지 알 수 있어야 한다.
- **20 명시적 승인 후에만 저장**: 기존 `interrupt()`·`Command(resume=...)` 흐름을 유지한다.
  - 등록·변경·취소·완료는 승인 뒤에만 실행한다. "알아서 해 줘"는 승인이 아니다. 기존 승인 버튼과 `action_id` 검증 규칙을 유지한다.
- **21 거절 시 유지**: 일정 데이터를 바꾸지 않는다. 필요하면 안전수칙이나 다른 방법을 안내하고, 작업 종류에 맞는 문장을 쓴다.
- **22 중복·오래된 승인 차단**: `action_id`와 `executed_action_ids`를 유지한다. 재실행·재호출에도 중복 적용하지 않는다. 오래된 버튼이 새 제안을 승인·취소하지 못하게 한다.
- **23 저장 직전 재검사**: 대상 존재, 기존 날짜·시간·버전이 제안 시점과 같은지, 충돌, 변경 제한, `action_id` 일치. 새 충돌이나 변경이 있으면 실행하지 않고 다시 확인한다.
- **24 저장 실패·파일 손상**: 파일 없음, 잘못된 JSON, 구조 오류, 읽기·쓰기 권한 없음, 저장 중 오류, 동시 요청
  - 오류 파일을 임의로 초기화하거나 덮어쓰지 않는다. 실패했는데 성공했다고 표시하지 않는다.
- **25 변경 이력**: `action_id`, `schedule_id`, 작업 종류, 변경 전·후 데이터, 승인 시각, 실행 시각, 실행 결과. 일정 데이터와 이력이 서로 어긋나지 않게 설계한다.

### E. 생활 기록 조회와 B기능 통합 준비
- **26 오늘·내일 일정**: 없으면 없다고 안내한다. 예정·완료·취소를 구분한다. 시간이 지났다는 이유로 완료로 바꾸지 않는다.
- **27 변경 이력 확인**: LLM 대화 기억이 아니라 실제 저장 기록을 조회한다.
- **28 A·B 공통 그래프 유지**: B 분기, 다중 턴, 보호자 도움 요청 승인 흐름을 손상시키지 않는다. A·B 상태를 섞지 않는다.
- **29 B 인터페이스 변경 금지**: `run_living_support()`, `execute_living_action()`, 승인 데이터, 반환 키, `living_evidence`, `payload.message`, `approval`, 멱등성 규칙을 유지한다. 팀원이 B 코드를 다시 개발하게 만들지 않는다.
- **30 생활 기록 통합 조회 준비**: "오늘 내가 부탁한 일이 뭐였지?", "내일 일정하고 보호자에게 요청한 물건 알려 줘", "오늘 한 일 정리해 줘"
  - A 일정·변경 기록 조회는 실제로 구현한다. B 기록은 명세 형식을 확인해 읽기 전용 함수나 어댑터를 준비한다.
  - B가 연결되지 않았으면 조회할 수 없다고 안내하고, 가짜 기록을 만들지 않는다.

### F. 테스트와 검증
- **31** 작업 전후 `a_outing.py`·`safety_rag.py`의 SHA-256을 비교한다.
- **32** 3·4단계 테스트를 실제로 실행한다. 기준 커밋·해시 검사가 의도된 확장과 충돌하면 보고하고, 새 기준으로 갱신해야 하는 검사만 설명한다.
- **33** 실제 `qwen2.5:3b`로 단일 질문과 다중 턴(날짜·시간·대상)을 검증한다. 모델이 제안을 만들지 못했는데 그래프가 돌았다는 이유로 성공으로 판정하지 않는다.
- **34** 승인 전 불변, 승인 후 해당 일정만 변경, 거절 시 유지, 반복 승인 시 중복 기록 없음, 재실행 후 유지, 대기 중 새 충돌이면 저장 차단. **운영용이 아닌 격리된 임시 저장소**에서 시험한다.
- **35** 단위, Mock LLM·가상 예보, 실제 코드 통합, 실제 Ollama, 실제 Open-Meteo, 실제 RAG, 실제 일정 파일 읽기·쓰기를 구분해 보고한다. 가상 예보를 실제 예보처럼 표시하지 않는다. 실행하지 않은 테스트를 통과로 보고하지 않는다.
- **36** `.venv-xpu`의 pyright로 문법·Pyright basic·타입 오류를 검사한다. `# type: ignore`나 검사 수준 완화로 숨기지 않는다. 잘못된 자료형 입력도 안전하게 처리한다.
- **37** 변경 코드·기능·테스트·남은 문제를 보고하고, 의미 있는 단위로 커밋을 제안한다. 커밋은 CLAUDE.md 규칙대로 승인 뒤에만 하고, Push·Merge·Rebase·Reset은 하지 않는다.

### 추가 권장 기능 38~42 (모두 구현)
- **38 신규 등록**: "내일 아침 여덟 시에 산책할 거야. 기억해 줘.", "다음 주 월요일 오후에 복지관 갈 거야.", "모레 오전 열 시에 친구 만나기로 했어."

## 3. GPU 자동 선택과 실행 환경 (요청 7절)
- 현재 환경: Windows 11, `C:\SafeMate-GitHub`, `.venv-xpu`, Python 3.14.6, Intel Arc 140T, PyTorch 2.15.0+xpu, Ollama, qwen2.5:3b, LangGraph 1.2.24
- 최종 결과물은 학교 NVIDIA GPU 서버와 Google Colab에서도 실행할 수 있어야 한다.
- **7.1 자동 선택**: CUDA → XPU → CPU 순서. 백엔드 존재, `is_available()`, 실제 텐서 연산 성공 여부까지 본다. 2단계 장치 검증 기능을 먼저 재사용하고, `a_outing.py`·`safety_rag.py`를 고치지 않고 상위 코드나 작은 모듈에서 해결한다.
- **7.2 수동 지정**: 자동, `--device cuda|xpu|cpu`를 지원한다. 지정한 장치를 쓸 수 없으면 조용히 바꾸지 않고 알린다. 자동 선택에서 실패하면 다음 장치를 검토하고 전환 이유를 기록한다.
- **7.3 실제 장치 확인**: 선택 장치, 임베딩 모델의 실제 장치, 텐서 연산 장치, 임베딩 결과와 차원, CPU 전환 여부와 이유. "GPU 인식"과 "실제 GPU 연산"을 구분한다.
- **7.4 Ollama 분리**: PyTorch가 XPU라고 Ollama도 Intel GPU라고 표시하지 않는다. 가능하면 `ollama ps`·서버 응답으로 따로 확인한다. 지원되지 않는 장치를 억지로 지정하지 않는다. qwen2.5:3b를 유지하고 새 모델을 받거나 바꾸지 않는다.
- **7.5 A·B 설정 분리**: A·B 임베딩 장치, RAG 색인, 모델 설정을 분리한다. 서로 덮어쓰지 않고, 요청마다 전역 환경변수를 바꾸지 않는다.
- **7.6 OS 호환**: Windows 절대 경로를 하드코딩하지 않고 `pathlib`·상대 경로, UTF-8 JSON, Linux·Colab, KST를 쓴다.
  - CUDA를 실측하지 못하면 Mock 검증과 구분하고, 학교 서버용 검증 명령과 환경별 설치 조건을 설명한다. 자동 선택을 구현했다고 모든 GPU 환경을 검증한 것으로 처리하지 않는다.

## 4. 저장소 설계 원칙 (요청 8절)
- 예시 구조: `schema_version`, `schedules[]`(schedule_id, title, start_at, end_at, city, category, status, reschedulable, version), `action_history[]`. 운영 코드에 현재 날짜를 고정하지 않는다.
- GitHub에는 공개 가능한 가상 초기 데이터와 구조만 올린다. 실행 중 생기는 데이터는 `.safemate/` 아래에 둔다.
- 최초 실행 때만 초기 데이터를 만들고, 기존 저장소를 덮어쓰지 않는다. 기준 시각을 주입할 수 있게 한다. 테스트는 `TemporaryDirectory`로 분리한다.
- 일정과 이력은 가능하면 한 JSON 문서에 함께 둔다. 임시 파일 + `os.replace()`로 원자적으로 저장한다. 읽기·검사·수정·쓰기 중 동시 실행으로 데이터가 사라지지 않게 보호한다.
- 단일 프로세스와 다중 프로세스의 보장 범위를 구분한다.
- `action_id` 기반 영구 중복 방지, 같은 id에 다른 내용이 오면 차단한다. 과도한 DB·외부 서비스를 쓰지 않는다.

## 5. 기존 3·4단계 확장 방향 (요청 9절)
- 흐름: 입력 → LLM 이해·의도 → 기존 일정 조회 → 날짜·시간 정규화 → 부족하면 질문 → 충돌·변경 가능 확인 → 필요하면 날씨·RAG → 후보 비교 → 제안 → LangGraph 승인 대기 → (승인) 재검사 후 JSON 저장 / (거절) 유지
  - 조회만 필요하면 승인 없이 끝낸다. B 요청은 기존 B 분기를 유지한다.
- **9.1 공개 함수 보존**: `run_outing_decision()`, `build_graph()`, `send_message()`, `press_button()`, `end_consultation()`, `turn_view()`의 호출 방식과 반환 호환성. 새 인자는 기본값 있는 키워드나 별도 어댑터로. 기존 반환 키를 지우거나 뜻을 바꾸지 않는다.
- **9.2 새 작업 종류**: 등록·변경·취소·완료. 기존 `propose_outing_time_change`를 유지한다.
  - `ALLOWED_ACTIONS`, `wrap_outing_proposal()`, `check_feature_result()`, `check_before_execute()`, 승인 카드, 실행 함수, 거절 안내와 일관되게 연결한다. B의 `request_caregiver_help`와 충돌하지 않게 한다.
- **9.3 실행 함수**: `apply_outing_change(approved_action)`을 우선 검토하고, 공통 실행 함수와 호환 래퍼를 쓸 수 있다.
  - 결과는 `{status, message, action_id, applied, mock, record, answer}`이다. 실제로 파일이 바뀌었을 때만 성공, 이미 처리했으면 기존 기록을 돌려준다.
- **9.4 실행 후 동기화**: 변경 뒤 다음 대화는 실제 저장된 최신 기록을 쓴다. 예) 17시로 바꾼 뒤 "몇 시에 가기로 했지?" → "오후 5시"(옛 14시를 말하면 안 됨).

## 12. 계획 검토(v1 → v2) 때 확정한 보완 조건 8개

   - 대상이 없거나 여러 개면 묻는다. 저장되지 않은 외출은 기존 일정을 고치지 않고 신규 등록을 제안한다. 날씨 기반 외출 상담의 제안도 저장소·충돌 검사를 거친다.
2. **의도 분류와 다중 턴**
   - 변경 동사만으로 변경 의도를 확정하지 않는다. 구분할 문장: "내일 일정을 바꿔 줘", "내일 일정 바꾸지 마", "시간을 바꿀 필요는 없어", "비가 오면 시간을 바꿀까?", "아니, 원래 시간에 갈래", "아까 말한 일정 말고 다른 일정이야", "저녁 일곱 시 아니고 여덟 시야", 상담 도중 날씨·생활지원으로 전환
   - 부정·정정·조건부·의도 변경을 반영한다. 모델이 낸 일정 ID가 존재한다는 이유만으로 사용자가 골랐다고 판단하지 않는다.
3. **시간·후보 탐색**
   - 자연어 표현(아침 8시, 저녁 7시, 밤 9시, 오후 네 시 반, 오후 네 시 십오 분, 지금부터 9시간 뒤 등)을 실제로 테스트하고, 모호하면 묻는다.
   - 07~21시는 자동 추천 기본값으로만 쓰고, 사용자가 명시한 시각은 막지 않는다. 자동 후보는 원하는 시간·충돌·소요 시간·날씨를 고려한다.
   - 날씨 나쁨과 확인 불가를 구분하고, 확인하지 않은 날씨를 근거로 추천하지 않는다. 완료·취소·진행 중·미래 일정의 완료 처리를 따로 검증한다.
4. **기존 테스트 호환**: G1(노드 6개 정확 비교)과 충돌하지 않도록 저장소 미연결 시 기존 그래프를 유지하고, 연결 그래프는 별도로 검증한다. 테스트를 삭제하거나 완화하지 않는다. 정당한 확장으로 바꿔야 하는 테스트는 이유와 범위를 보고하고 기존 기능 유지 회귀 테스트를 추가한다.
5. **영구 저장·승인 안전**
   - 일정·이력을 한 JSON에 두고, 저장 직전에 id·버전·전후 데이터·중복 `action_id`·충돌·제한을 검증한다.
   - 미승인·거절·취소 시 데이터를 바꾸지 않는다. 저장 실패·손상·잠금 실패 시 기존 데이터를 보존한다.
   - 비정상 종료로 남은 잠금 파일의 처리와 보장 범위를 문서화한다. 최초 초기화 외에는 사라지거나 손상된 저장소를 다시 만들지 않는다. 모든 테스트는 임시 저장소를 쓴다.
6. **CUDA·XPU·CPU**
   - 진단 명령뿐 아니라 실제 실행 경로에도 연결한다. 순서대로 탐색하며 임베딩 모델 로딩·연산 성공까지 확인하고, 실패 원인을 기록한 뒤 다음 장치로 넘어간다. 수동 지정 실패는 바꾸지 않는다.
   - PyTorch·Ollama 장치를 구분하고, 모델이 아직 적재되지 않은 상태를 CPU 실행으로 보고하지 않는다. Windows·학교 서버·Colab이 같은 구조를 쓴다.
   - CUDA를 실측하지 않았으면 미검증으로 표시한다. Colab 임시 파일시스템과 영구 저장 한계를 안내한다. 패키지를 바꾸지 않는다.
7. **실제 LLM 검증**
   - M·I·L·R 구분을 유지한다. 그래프 무오류 실행과 모델의 올바른 의도·유효 제안을 구분한다.
   - 실제 Ollama + 명시된 가상 예보로 "조회 → 변경 요청 → 충돌 → 대체 제안 → 승인 → JSON 수정 → 재조회 → 재실행 후 확인"과 거절 시 파일 불변을 검증한다.
   - 모델이 제안을 못 만들면 모델 판단 실패로 기록하고 안전한 대체 답변과 구분한다. 성공할 때까지 무제한 재시도하거나 결과를 고르지 않는다. 모델 교체는 결과를 본 뒤 사용자가 결정한다.
8. **B 계약·규칙 유지**: 명세 2장 불변, B 구현·가짜 기록 금지, 1·2단계와 3단계 테스트 파일 보호, 필요한 3·4단계만 최소 확장, 일정 기능은 신규 모듈로 분리, 주석·CLAUDE.md·PROJECT_SPEC 규칙 준수, 42개 요구사항 대응표 유지

## 13. 구현 승인 때 덧붙인 조건 (계획 v2 승인 메시지)
1. 잠금 파일이 30초 넘게 남았다는 이유만으로 사용 중일 수 있는 잠금을 강제로 해제하지 않는다. 안전하게 판단할 수 없으면 저장을 중단하고 복구 방법을 안내한다.
2. 구현 단위마다 기존 회귀 테스트를 확인한다. 3·4단계 코드 변경과 R1 기준 변경이 서로 의존하면 같은 커밋 단위로 묶을 수 있다.
3. 날씨·RAG·B 인터페이스를 보호하고, 42개 요구사항에 대응하는 테스트를 유지한다.
4. 실제 LLM 테스트에서 그래프 성공, 모델 판단 성공, 일정 변경 제안 성공, 실제 저장 성공을 구분해 보고한다.
5. 자동 선택을 실제 실행 경로에 연결하고, 현재 환경에서는 XPU·CPU를 실측한다. CUDA는 실측하지 않았으면 미검증으로 표시한다.
6. 한국어 주석 형식, 모듈 분리, 타입 오류 0개를 유지한다.
7. 승인되지 않은 패키지 설치, 유료 API, 모델 다운로드·교체를 금지한다.
8. 단위마다 변경 파일·테스트 결과·문제·한계를 보고하고, 커밋은 별도 승인 뒤에만 한다. Push·Merge는 하지 않는다.

## 14. 구현 단위별 검토에서 추가로 확정한 규칙
- **5-1 검토**: `validate_document()`는 해시할 수 없는 id를 `schema_error`로 처리한다. 잠금 정보 기록에 실패하면 내가 만든 잠금 파일만 정리한다(다른 프로세스 잠금은 지우지 않는다).
- **5-2 검토 (7개)**
  - LLM이 고른 id는 후보가 여러 개면 확정하지 않는다(`multiple` + `llm_suggested`).
  - "A 말고 B" 같은 정정을 반영하고, 애매하면 다시 묻는다.
  - 예보는 1단계 계약·3단계 규칙으로 검증해 `signal`·`no_signal`·`unknown`으로 구분한다(`good`·`bad`는 쓰지 않음). 신호 없음을 안전 보장으로 표현하지 않는다.
  - 자정을 넘는 시각 식별을 올바르게 한다.
  - 저장 직전 시각은 잠금을 잡은 뒤에 읽고, 대기 중 끝난 일정의 취소를 차단한다.
  - 승인 데이터와 실제 변경 내용(소요 시간·변경 가능 항목·등록 범위)을 대조한다.
  - 큰 상대 날짜의 OverflowError와 서로 충돌하는 표현을 처리한다.
- **5-3 요청 조건 (15개 요지)**
  - LLM이 의미를 판단하고 Python은 검증·제한적 보정만 한다. 기존 날씨·외출·안전수칙·B 분류와 반환 계약을 유지한다.
  - "내일 일정 좀 바꿔 줘", "시간은 네가 알아서 정해 줘", "아까 바꾼 일정", "오후 네 시 말고 저녁 일곱 시"를 고려하고, 부정·정정·모호 표현을 잘못 확정하지 않는다.
  - `signal`·`no_signal`·`unknown`과 `llm_suggested` 규칙을 이후 연결에서도 유지한다.
  - LLM은 승인을 대신하거나 저장소를 수정하지 않는다. B 계약은 불변이다. 1·2단계와 5-1·5-2 완료 코드는 결함이 없으면 고치지 않는다.
  - 3단계 스키마·공개 함수는 확장 범위만 바꾸고 하위 호환을 지킨다. 해시 검사와의 충돌은 승인 범위인지 구분해 보고한다.
  - 장치 자동 선택 본격 구현은 5-5단계, 이번 단위만 작업한다.
- **5-3 커밋 제목 형식**: 5단계 하위 단위는 `feat: [5-N단계] …`처럼 쓴다. (예: `feat: [5-3단계] LLM 일정 의도 분류 보완 및 일정 넘김 경로 추가`)
