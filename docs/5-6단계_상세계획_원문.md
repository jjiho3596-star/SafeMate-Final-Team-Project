## 5·6·7. 시나리오, 입력·기대 결과·반복 횟수, Mock과 실제의 구분
**공통 규칙**
- 대상 표기: [실Q]는 실제 qwen2.5:3b, [가L]은 가상 LLM. [가예]는 고정 가상 예보, [실예]는 실제 Open-Meteo.

- 반복 횟수는 코드 상수로 고정한다. CLI로 바꿀 수 없게 한다.
- 대표 결과를 고르지 않는다.
  - 결과를 보고 다시 실행하거나 일부 회차만 다시 돌리지 않는다.

## 8. 실제 데이터 종합 연동 방법
- `tod.Harness(llm=CountingLLM(od.call_ollama), weather="real", city="real", rag="real", now=<실제 현재 KST>)`
- 임시 저장소는 실제 현재 시각으로 초기화한다(초기 일정이 상대 날짜이므로 자연스럽게 맞춰진다).
- `build_graph(schedule_store=임시, a_device="auto", a_index=None)`로 시작한다. 장치는 자동 선택하고 색인은 첫 검색 때 실제로 준비한다(DeviceSelectionError·IndexDeviceError 경로가 그대로 적용됨).
- 시간 측정 감싸개
  - `od.get_outing_weather`와 `od.search_safety_guidance`를 원래 함수를 그대로 부르는 시간 측정 함수로 감싼다. 응답은 바꾸지 않는다.
  - 기록 항목: 호출 수, 걸린 시간, `status`, 예보 원래 값, 검색 출처
- 실제 예보 회차에는 `fetched_at`과 예보 대상 시각을 기록한다. 실제 날씨에 위험이 없으면 "제안 없음"이 정상 결과일 수 있다. 실제 결과에 따라 판정 칸이 '후보 없음(정상)'인지 '제안 생성'인지로 나뉜다.

## 11. 실제 Ollama 추론 장치 검증 방법
- PyTorch 장치 보고와 따로 측정한다(`du.ollama_report(probe=True)`)
  - 서버 연결, 모델 설치
  - 호출 전 `/api/ps`
  - 실제 짧은 호출
  - 호출 직후 `/api/ps`(`size`, `size_vram`)
  - 같은 서버일 때만 `ollama ps`
- 판정
  - `size_vram > 0`: GPU 메모리 적재. 전체 또는 부분이며, 모든 연산이 GPU라는 뜻은 아니다.
  - `0`: GPU 메모리 사용이 보고되지 않음.
  - 그 밖: 측정 실패
- GPU 종류는 `nvidia-smi`에 ollama 프로세스가 보일 때만 "NVIDIA"로 적는다. 추론 백엔드(CUDA 등)는 확인할 근거가 없으면 적지 않는다.
- 현재 PC의 CPU 추론(`size_vram` 0, 100% CPU)은 그대로 기록한다. **Colab 결과로 학교 서버 검증을 대신하지 않는다.**
- 4.1~4.9의 L층 묶음마다 시작 전 `/api/ps`로 cold(미적재)·warm(적재) 상태를 기록하고, 끝난 뒤의 상태도 기록한다. 모델을 일부러 내리지 않는다(`ollama stop`은 사용자가 원할 때만).

## 12. 성공 판정과 결함 분류
**회차별 지표 11개** (서로 섞지 않음)

| 번호 | 지표 | 기록 이름 |
|---|---|---|
| 1 | 그래프 실행 성공 | graph_ok |
| 2 | LLM 의도 분류 성공 | intent_ok |
| 3 | LLM 상황 판단 성공 (일정 이해 칸이 기대와 맞음) | judgment_ok |
| 4 | 유효한 승인 제안 | proposal_ok |
| 5 | 승인·거절의 올바른 반영 | decision_ok |
| 6 | 실제 저장 성공 | saved_ok |
| 7 | 재조회 성공 | requery_ok |
| 8 | 재실행 후 영구 유지 (새 객체·새 그래프·별도 프로세스) | persist_ok |
| 9 | 안전한 대체 응답 (모델이 틀렸을 때 잘못된 저장 없이 질문·안내) | safe_fallback |
| 10 | 외부 API·RAG 실행 성공 | external_ok |
| 11 | 실제 장치 측정 성공 | device_ok |

- 모델이 틀렸지만 Python이 막은 경우: judgment_ok=False이고 safe_fallback=True로 따로 센다.
- 그래프가 성공했다고 해서 모델 판단 성공으로 세지 않는다.
- **원인 구분 방법** (M_AG6 방식)
  1. 회차마다 모델의 실제 이해 JSON을 기록한다.
  2. 실패 회차의 이해가 기대 필수 칸과 같은데 결과가 다르면 '프로그램 결함 후보'로 본다.
  3. 그 실제 출력을 가상 LLM에 넣어 결정적으로 다시 실행해 본다.
  4. 같은 결과가 재현되면 프로그램 결함으로 확정한다. 재현되지 않으면 모델 판단 문제로 본다.

**결함 등급**
| 등급 | 해당하는 경우 | 처리 |
|---|---|---|
| S1 치명 (5-6 완료를 막음) | 승인 없는 저장, 거절 후 저장, 잘못된 대상 변경, 중복 저장, 충돌 일정 저장, 보호 일정 변경, 운영 저장소 접근, `applied=False`인데 성공 표시, 그래프 예외 중단, 조회하지 않은 날씨·출처 표시, 보호 파일 변경, 장치 오보고(CPU를 GPU로 보고하는 등) | 즉시 중단하고 보고 → 최소 수정 승인 → 수정 → 같은 묶음 전체 재측정 |
| S2 프로그램 결함 (완료 전 수정 또는 사용자가 이관 결정) | 올바른 이해인데 잘못된 결과, 다중 턴 상태 손실, 질문 반복, 안내 문구 모순, 장치 선택·보고 오류 | 원인과 최소 수정 범위를 먼저 보고 |
| M 모델 한계 (문서에 기록) | 모델 오분류·칸 누락을 Python이 안전하게 처리한 경우, 응답 시간 | 수치로 보고. 키워드 if문을 대량으로 늘리거나 LLM 역할을 빼는 수정은 하지 않음 |
| E 환경 | 네트워크, Open-Meteo, Ollama 미준비, 접근 불가 환경 | 환경 오류로 따로 기록, 미검증 표시 |

## 20. 외부 검토 보완 (조건부 승인 반영, 이번 승인 범위는 5-6-A까지)
**확인한 코드 사실**

  - 테스트에서 이 값을 바꾸지 않는다.

  - 등록: 모델이 `request_mode=conditional`이라고 하면 미지원 안내. `request` + `avoid_rain`이면 즉시 예보 확인 경로(AG41)로 간다.

  - 기대값은 다음과 같이 정한다.
    - AG41 문장: 즉시 예보 확인 경로가 나와야 PASS.
    - 미지원 안내가 나오면 판단 FAIL·안전 PASS(원인: 모델 분류·명세 모호)로 기록한다.
    - 조건 없이 카드를 만들면 FAIL(조건 무시 제안)이다.

## 21.2 정확한 원인
- `schedule_agent.handle_create()`와 `handle_update()`는 함수 앞부분에서 `ambiguous_city()`를 호출한다.
  - `ambiguous_city()`는 지역이 모호하면 `ask(..., "city")` 하고 바로 return한다.
  - 날짜·시각 해석(`resolve_new_time`), 대상 식별(`_target_for`), 소요 시간 해석보다 **먼저** 실행된다.
- 그런데 이번 턴의 값(`t.u`)은 다음 턴으로 넘어가지 않는다. 다음 턴에 남는 것은 초안(`draft`)뿐이다.
  - 사용자 발화 표현은 첫 턴의 `t.u`에만 있다. 초안에 옮겨지는 것은 날짜·시각 계산이나 대상 확정 뒤다.
  - 그래서 지역 질문에서 return하면 이 표현들이 사라진다.
- 기존 보관 장치 두 가지는 이 return보다 늦게 실행된다.
  - 대상 질문 때 새 시각 표현을 `pending`에 보관하는 장치(변경 1128줄)
  - 날씨 지역 질문 때 시각·시간대를 보관하는 장치(`preference_gate`의 `pending.start`, `keep_auto_range`의 `pending.period`)
- C2가 오늘 날짜를 내는 이유: 다음 턴에 날짜가 없으면 `resolve_new_time()`이 위임일 때 `day or now.date()`를 쓴다.
- `_clean_draft()`와 `keep_auto_range()`는 원인이 아니다. 둘 다 정상이고 재사용한다(`pending`은 문자열만 남기는 기존 검사를 그대로 탄다).

## 21.3 최소 수정 (schedule_agent.py만, 공개 함수·반환 구조·승인 규칙 불변)
- **보관할 표현 목록 상수:** 사용자가 말한 그대로의 문자열이고, 이미 발화 근거 확인을 거친 값이다.
  - `CITY_HELD_CREATE = ("date_text", "time_text", "shift_text", "shift_base", "duration_text", "reason_text")`
  - `CITY_HELD_UPDATE = ("target_text", "date_text", "time_text", "reason_text") + CHANGE_WORDS`
  - 기존 `pending` 키(start, period, CHANGE_WORDS)와 겹치지 않는다. 변경의 CHANGE_WORDS는 기존 대상 질문 보관과 **같은 키·같은 이어 쓰기 규칙**(1139~1146줄)을 탄다.
- **`ambiguous_city(t, draft, held=())`** (기본값 덕분에 기존 호출과 호환, 외부 호출 없음)
  - 질문하기 전에 `draft["pending"]`에 `t.u`의 비어 있지 않은 held 값을 보관한다(shift_base는 "unknown"이면 보관하지 않음).
  - `draft["other_day_ok"] = draft["other_day_ok"] or t.u["other_day_ok"]`도 함께 둔다(초안에 이미 있는 칸).
- **새 도우미 `restore_held(t, draft, keys)`**
  - `handle_create`·`handle_update`에서 초안을 이어받은 직후 부른다.
  - 보관한 값을 `pending`에서 꺼내 `t.u`에 채운다. **이번 턴에 새로 말한 값이 있으면 그 값이 우선**한다(정정 우선, 기존 `period` 이어 쓰기 규칙과 같음).
  - 규칙 기록: `city_question_held_restored`
  - 다시 모호한 답("광주")이면 이어 쓴 값을 그대로 다시 보관하므로 정보가 사라지지 않는다.
- **결과**

## 22.2 D1 최소 수정 (21.3을 대체: 그룹 단위 복원)
**보관.** `ambiguous_city(t, draft, held=...)`가 지역을 묻기 전에 다음을 보관한다.
- 보관 위치는 `draft["pending"]`의 **별도 키 `hold:<칸>`**이다.
  - 기존 pending 키와 섞이지 않는다.
  - `_clean_draft`의 문자열 검사를 그대로 탄다.
- 등록에서 보관하는 칸
  - 날짜: `date_text`
  - 시각: `time_text`, `shift_text`, `shift_base`
  - 그 밖: `duration_text`, `reason_text`
- 변경에서 보관하는 칸
  - 대상: `target_text`, `date_text`, `time_text`
  - 새 날짜: `new_date_text`
  - 새 시각: `new_time_text`, `shift_text`, `shift_base`
  - 그 밖: `reason_text`
- **'지금부터' 상대 시각**은 말한 순간 기준의 절대 시각을 `hold:start`로 보관한다(`sv.resolve_shift(shift, t.now)`). 지역 질문을 거치는 동안 기준이 밀리지 않게 하기 위함이다.
- '원래 일정 기준'(schedule) 상대 시각은 대상의 저장 시각이 기준이라 밀리지 않으므로 표현 그대로 보관한다.
- `draft["other_day_ok"]`도 남긴다(기존 칸).

**복원.** `restore_held(t, draft, kind)`는 초안을 이어받은 직후 한 번 실행한다.
1. 이번 턴에 그 그룹의 값을 하나라도 말했으면, 그 그룹의 보관 값은 버린다. 정정이 우선하고, 그룹 안의 표현은 서로 배타적이다.
   - 상대 → 지역 + 직접 시각: 직접 시각이 이긴다.
   - 직접 → 지역 + 상대 시각: 상대 시각이 이긴다.
   - 시간대 → 지역 + 직접 시각: 직접 시각이 이긴다.
2. 날짜만 말하면 다음과 같이 처리한다.
   - 보관한 직접 시각·시간대는 유지한다.
   - 보관한 상대 시각(`shift_text`·`hold:start`)은 버리고 시각을 다시 묻는다. 새 날짜와 상대 시각을 임의로 조합하지 않는다.
3. 변경에서 이번 턴에 대상 표현이 있거나 `exclude_previous_target`이면 보관한 대상 표현을 버린다. 대상 날짜·시각과 새 날짜·시각(`new_*`)은 다른 그룹이라 섞이지 않는다.
4. 남은 값은 `t.u`에 채운다.
   - `hold:start`는 기존 `pending["start"]` 경로(등록 1243줄, 변경 1142줄)로 옮겨 기존 이어 쓰기 규칙을 그대로 쓴다.
   - 규칙 기록: `city_question_held_restored`
5. 다시 모호하게 답하면 이어 쓴 값을 다시 보관한다.
6. 부정·상담 끝내기·새 요청은 초안을 지우거나 새로 만들므로 보관 값이 다시 적용되지 않는다.

**바꾸지 않는 것:** `resolve_new_time`, `keep_auto_range`, `_clean_draft`, `preference_gate`, 기존 pending 이어 쓰기 규칙, 공개 함수·반환·승인 규칙. 약 30~40줄 추가.

1. 신규 테스트 → 수정 전 실행 기록 → 수정 → 같은 테스트로 전후 비교
2. expectedFailure·skip 제거 → M·I 전체 → 기본 회귀 4종 → py_compile·Pyright·3.11 AST → 추적·untracked 파일 공백 검사 → 보호·로그·Git 확인
3. 보고 후 중단한다. 커밋은 사용자 검토 뒤에 정한다.

## 24.4 최소 수정 방법
**P1 (schedule_service.py)**
- 3단계 `WORD_NUMBERS`는 그대로 둔다. 일정 서비스 안에만 `NATIVE_TEENS = {"열세":13 … "열아홉":19}`, `NATIVE_HOURS = {**WORD_NUMBERS, **NATIVE_TEENS}`를 두고, `NATIVE_HOUR_RE`에 열세~열아홉을 긴 것부터 추가한다.
- `_partial_number(text)`: 정규화한 뒤에도 다음이 남으면 True다. 이 경우 부분 해석하지 않는다.
  - 숫자 낱말 두 개가 붙은 '시간'·'주' 표현(두세·한두·스물두·열두 주 등)
  - 세 자리 이상 숫자 + 시간
  - 네 자리 이상 숫자 + 분
- 처리
  - `parse_minutes`: None을 돌려준다(기존 '10분~12시간 사이로' 질문).
  - `resolve_shift`: `{"ambiguous": "시간을 정확히 알 수 없어요. 숫자로 다시 알려 주세요(예: 13시간)."}`
  - `parse_day`의 주 단위: 같은 ambiguous를 돌려준다.
- 정상 표현의 경로는 그대로다. 스물·스무(20~24시간)는 지원 범위에 넣지 않는다. 스무 시간은 지금처럼 None이고, 스물두 시간은 부분 해석 대신 되묻는다.

**D12 (schedule_agent.hold_said)**
- 날짜 묶음(등록 `date_text`, 변경 `target_text`와 함께 있는 `date_text`, 변경 `new_date_text`)을 보관할 때 `sv.parse_day(text, t.now)`를 실행한다.
  - 날짜가 확정되면 ISO 날짜(예: 2026-11-26)로 보관한다. parse_day·대상 찾기가 ISO를 그대로 읽는 것을 확인했다.
  - "그날·다음 날"처럼 앞 대화 기준이라 확정되지 않으면 표현 그대로 보관한다.
- 다시 모호하게 답하면 ISO가 다시 보관되므로 밀리지 않는다.
- 이번 턴에 새 날짜를 말하면 기존 규칙대로 새 값이 이기고, 말한 시각 기준으로 계산한다(00:05의 "모레" = 11-28).

**D13 (schedule_agent.handle_create)**
- 다음 세 질문 직전에 D1의 `hold_said(t, draft, "create")`를 부른다.
  - 날짜 질문(시각만 있음)
  - 제목 질문
  - 소요 시간 질문
- 다음 턴에는 맨 앞의 `restore_held`가 이어 쓴다. 새 질문 구조나 질문 순서 변경은 없다.
- 규칙 이름은 `f"{draft['awaiting']}_question_held_restored"`로 바꾼다. 지역 질문이면 기존 이름 `city_question_held_restored` 그대로다(AG48 유지).
- 잘못 다시 쓰지 않게 하는 보호
  - `restore_held`에서 초안에 제목이 있는데 이번 턴의 제목이 다르면 새 등록 요청으로 보고 보관 값을 모두 버린다. 기존 `_dispatch`는 진행 중인 등록 초안을 이어 쓰므로 이 보호가 필요하다.
  - 부정·상담 종료는 기존대로 초안을 지운다.
- 오전·오후 질문은 이미 `draft["date"]`가 남아 있어 바꾸지 않는다. 변경은 기존 보관으로 손실이 없어 바꾸지 않는다.
- 영향: 기존 흐름(지역이 모호하지 않거나 없는 등록)에서도 날짜를 답하면 다시 묻지 않고 카드가 나온다. 기존 결함의 수정이다.

- 새 `forecast_at(obs, card, spec)`는 날씨 조건 판정과 승인 전 검사가 같이 쓴다.

  - unknown 포함 → FAIL(불완전 예보).
  - 비 있음·없음이 섞이면 → FAIL(상충 기록).
  - 모두 확인됐고 비 신호 없음일 때만 PASS.

- 식별자를 얻지 못하는 파일 시스템이면 기존 token 비교로만 판단하고, 남으면 안내한다.

## 25.3 수정 대상과 방법 (공개 함수·반환 구조·승인 규칙·a_outing 계약·호출 상한 4회 유지)
**schedule_agent.py (D21)**
1. `Turn`에 한 턴 안에서만 쓰는 예보 기록 `forecasts: dict`를 추가한다.
2. 새 함수 `fetch_span(t, city, start, end)`
   - 구간 계산
     - [start, end)와 겹치는 정시 구간을 모두 확인한다. 14:00~15:00은 14시 하나, 14:30~15:30은 14시·15시, 14:30~16:30은 14·15·16시다.
     - 자정을 넘기면 다음 날 0시 구간도 포함한다.
     - 첫 구간은 시작 시각 그대로, 이후 구간은 정시(HH:00)로 기존 `fetch_forecast`를 부른다.
     - (지역, 정시 구간)이 같으면 한 턴 안에서 다시 조회하지 않는다. 호출 상한은 그대로 4회다.
   - 판정 결과 합치기
     - 하나라도 unknown이면 전체 unknown이다(상한·예보 기간 밖·누락·조회 오류). 사유에 확인하지 못한 구간 시각을 적는다.
     - 신호는 모든 구간의 합집합이다.
     - `parts`에 구간별 결과를 담는다.
   - 예보 값 합치기
     - `weather`에는 LLM 후보 비교와 이유 검증용 값을 담는다. 강수량·강수확률·풍속·기온은 구간 최댓값이다.
     - 한파 비교용으로 `coldest`(최저 기온)를 따로 둔다.
3. 명시적인 날씨 조건(preferences)이 있는 경로만 `fetch_span`을 쓴다. 날씨 조건이 없는 일반 일정과 조회 경로는 기존 단일 조회를 그대로 쓴다(AG26 등 보존).
   - `preference_gate`: 인자로 종료 시각을 받는다. 등록은 draft 소요 시간(없으면 기본 60분), 변경은 원래 소요 시간이다.
   - `choose_slot`(preferences가 있을 때): 원래 시각과 후보 모두 일정 전체 구간을 확인한다.
   - `handle_conditional`: 일정 전체 구간에서 조건(비)을 판단한다. 어느 한 구간이라도 비면 조건이 충족된 것이고, unknown이 있으면 조건 판단 불가다.
   - `offer_update`의 날씨 조건 경로: 원래 시각도 `fetch_span`으로 확인한다(같은 턴 기록을 다시 써서 추가 호출 없음).
4. 우회 차단: `offer_update`·`offer_create`의 충돌 대체 분기에서 시각이 바뀌면 `verified=False`로 되돌려 대체 시각을 다시 확인한다.
5. 표시와 안내
   - `weather_block`: `parts`를 구간별 줄로 풀어 적는다(예: '바꿀 시각 오후 2시 30분 …', '이어지는 구간 오후 3시 …').

## 25.5 영향
- **예보 조회 수**
  - 걸친 구간을 추가로 조회하지만, 같은 구간은 한 턴에 한 번만 조회한다(⑥의 위임은 4회 → 3회 예상).
  - 상한 4회는 유지한다. 그래서 후보 구간이 많으면 뒤 후보는 unknown이 되어 고르지 않는다('찾지 못해' 안내가 늘 수 있음, 안전한 쪽).
- **예보 표시**: 구간이 둘 이상이면 줄이 늘어난다. 날씨 조건이 없는 경로의 표시는 바뀌지 않는다.
- **RAG**: 고른 시각 전체 구간에 위험 신호가 있을 때 주제를 모든 구간에서 고른다. 두 번째 구간 강풍처럼 전에는 놓치던 공식 수칙이 붙을 수 있다.
- **LLM 후보 선택**
  - 문맥 값이 구간 최댓값(한파는 최저 기온)으로 바뀐다.
  - 이유 검증도 같은 값을 쓴다.
  - 걸친 구간에 비가 있는 후보는 고를 수 없게 된다. 모델이 고르면 Python 검증이 거부하고 대체 규칙(python_fallback)으로 고른다.
- **기존 테스트**
  - 날씨 조건이 있는 기존 기대값(AG22 15:00, AG37 19:00, LV2 등)은 후보가 정시 시작이거나 같은 결과라 유지될 것으로 예상한다.
  - 기존 기대값이 바뀌면 고치지 않고 멈춘 뒤 보고한다.
- **A기능**: 출발 시각 판단과 a_outing 계약은 바꾸지 않는다. outing_decision은 숫자 경계 규칙만 바뀐다.

  - 새 함수 `weather_contract_problems(call)`가 운영 `read_weather`와 같은 계약을 독립적으로 검사한다(`od.departure_hour_window`, `od.FIELDS` 사용). 검사 항목: 지역, data_kind, 출처, outing_at = 요청 날짜·시각(KST), hour_start·hour_end 정시 구간, +09:00, missing_fields·status 일관성.

  - `rain_at`: 구간의 기록 중 하나라도 계약이 어긋나면 FAIL이다(PASS 금지, 승인 전 검사도 같은 함수).
  - `judge_weather`: 필수 호출의 계약 불일치는 FAIL("응답 계약 불일치, 원인 미확정")이고, network_error는 지금처럼 ENV_ERROR다.
- **D26**
  - 새 함수 `expected_rag_topics(spec, obs, card)`
    1. 시나리오의 `rag_topics`
    2. 없으면 카드 전체 구간 예보의 위험 주제
    - 출처 파일에서 주제를 거꾸로 만들지 않는다. 기대 출처 파일은 `rag_file`과 기대 주제의 파일로 따로 둔다.
  - `judge_rag_calls(required, topics)`
    - 기대 주제마다 그 주제의 공식 질문 검색이 1건 이상 정상이어야 PASS다.
    - 빠진 주제가 있으면 FAIL("필수 주제 [대설] 검색 없음")이다.
    - 필수 주제 검색의 오류는 기존 규칙대로다(환경 근거가 있으면 ENV_ERROR, 없으면 원인 미확정 FAIL).
    - 다른 주제 검색은 보조이고, 실패하면 경고로 남긴다.
    - 인자를 주지 않으면 기존 동작이다(LV54 호환).
  - `rag_topic`: 공식 질문으로 시작하지 않는 질의는 주제 낱말이 하나만 들어 있을 때만 그 주제로 본다(합성 질의 '강풍 질문' 호환). 운영 코드는 항상 공식 질문으로 시작한다.
  - 시나리오 상수: LV8C에 `rag_topics: ["강풍"]`을 추가한다(17시 강풍 시나리오 의도 그대로, 호우로 넓히지 않음). 실측 전 고정이다.
  - **결정 필요(LV8-safety)**: 현재 `rag_topics: ["한파", "대설"]`
    - A기능은 예보 신호와 사용자가 말한 주제로 RAG 주제를 고른다. "추운 날 외출할 때 조심할 거"에서 사용자가 말한 위험은 한파다.
    - 권장: 필수 한파, 대설은 보조(검색하면 성공해야 하고, 빠져도 FAIL은 아님).
    - 대안: 둘 다 필수. 이 경우 모델이 대설을 고르지 않으면 rag_call이 FAIL로 측정된다.
  - 본문 관련성은 계속 REVIEW다.
