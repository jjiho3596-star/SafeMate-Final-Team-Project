# SafeMate 5단계 구현 계획: 자연어 일정 관리와 승인 후 영구 저장

## Context
- 4단계 그래프는 승인 흐름(`interrupt`·`Command`, `action_id`, 실행 직전 재검사)을 이미 갖고 있습니다. 하지만 승인 뒤 실제로 바뀌는 데이터가 없고, `a_executor=None` 상태입니다.
- 실제 qwen2.5:3b는 일정 변경 요청을 `weather_question`으로 분류해서 일정 변경 제안이 나오지 않았습니다(L2를 두 번 실행해 두 번 모두 확인).
- 5단계의 목표
  - 가상 일정 JSON 저장소를 만듭니다.
  - 자연어로 일정을 조회·등록·변경·취소·완료 기록할 수 있게 합니다.
  - 날씨·RAG·일정 충돌을 함께 판단해 제안합니다.
  - 기존 LangGraph 승인을 거친 뒤에만 파일에 저장합니다.
  - 학교 CUDA 서버·Colab에서도 돌 수 있도록 장치를 자동 선택합니다.
- 범위 밖: B기능 실제 구현, Gradio, 외부 캘린더 연동.

## 1. 현재 코드에서 5단계와 관련된 실제 동작
- **3단계** `run_outing_decision()`
  - 이해 LLM 1회(15키 스키마, 의도 6개) → Python 정규화 → 날씨·RAG → 답변 LLM → 검증 → 대체 답변 순으로 처리합니다.
  - `schedule_change` 의도는 "저장된 일정"이 아니라 사용자가 말한 외출 시각을 기준으로 2시간 뒤 한 구간만 비교합니다(`compare_alternative`). 일정 저장소 개념이 없습니다.
  - 테스트에 걸린 제약
    - `ROUTES == INTENTS ∪ {needs_clarification, error}` (A 계약 테스트)
    - 이해 스키마는 키 15개가 정확히 같아야 합니다. 가짜 LLM 테스트가 이 형식을 씁니다.
- **4단계** `safemate_graph.py`
  - 노드 6개, `ALLOWED_ACTIONS`(type → source·feature), `executors={"A","B"}`
  - 승인 카드는 A·B 두 가지, 거절 문장은 A·B 두 가지만 있습니다.
  - R1 테스트가 `outing_decision.py`의 해시를 `c4e2ca0`과 비교합니다. 5단계에서 이 파일을 고치므로 충돌합니다(16절).
- **2단계** `configure_embedding_device(requested)`: 지정한 장치에서 `is_available`과 텐서 연산을 확인하고, 실패하면 `SafetyError`를 냅니다. `load_embeddings()`와 `verify_embedding_device()`가 가중치·토큰·출력 장치와 384차원을 확인합니다. **자동 선택 기능은 없습니다.**

## 4. 가상 일정 데이터 구조
```json
{"schema_version": 1, "store_id": "uuid", "created_at": "...+09:00", "updated_at": "...",
 "schedules": [{
   "schedule_id": "schedule_001", "title": "시장 장보기", "aliases": ["장보기", "시장"],
   "start_at": "2026-11-26T14:00:00+09:00", "end_at": "2026-11-26T15:00:00+09:00",
   "city": "인천", "category": "outing", "status": "scheduled", "reschedulable": true,
   "version": 1, "source": "seed", "created_at": "...", "updated_at": "...",
   "completed_at": null, "cancelled_at": null}],
 "action_history": [{
   "action_id": "32hex", "content_hash": "sha256", "operation": "update", "schedule_id": "schedule_001",
   "before": {...}, "after": {...}, "reason": "...", "approved_at": "...", "executed_at": "...", "result": "applied"}]}
```
- `category`: `outing`(실외 외출, 날씨 판단 대상), `appointment`(약속·기관 방문), `home`, `other`
- `status`: `scheduled`, `completed`, `cancelled`. **시간이 지나도 자동으로 완료 처리하지 않습니다.** 조회할 때만 "시간이 지났어요(완료 기록 없음)"로 표시합니다.
- `reschedulable: false`이면 변경 제한 일정입니다. SafeMate는 이 일정을 변경하거나 취소하지 않습니다. 완료 기록은 허용합니다.
- 초기 데이터에는 날짜를 고정하지 않습니다. `{"day_offset": 1, "start": "14:00", "minutes": 60, ...}` 형식으로 두고, 처음 만들 때 주입한 현재 시각 기준으로 날짜를 계산합니다.
- 기본 일정 4개
  - 내일 14:00 시장 장보기 (외출, 변경 가능)
  - 내일 16:00 복지관 방문 (변경 제한)
  - 3일 뒤 10:00 병원 진료 (90분, 변경 제한)
  - 오늘 08:00 산책

## 5. 조회·충돌 검사·후보 탐색 알고리즘 (`schedule_service.py`)
- **조회**
  - 날짜·범위(오늘, 내일, 이번 주), 대상, 다음 일정(현재 KST 이후 `scheduled` 중 가장 이른 것), 남은 일정, 진행 중(시작 ≤ 지금 < 끝)을 계산합니다.
  - 이력은 `action_history`에서 읽습니다. 저장소를 매번 다시 읽고, State에 일정을 캐시하지 않습니다.
- **대상 식별** `find_targets()`
  1. 조작 종류에 따라 후보 상태를 거릅니다. 변경·취소·완료는 `scheduled`만 대상입니다.
  2. 날짜·시각·시간대가 주어지면 그것으로 거릅니다.
  3. 제목·별칭 문자열을 비교하고, LLM이 고른 `target_ids`가 있으면 그 id와 교집합을 구합니다. LLM이 없는 id를 내면 버립니다.
  4. "아까 바꾼·등록한 일정"은 이력의 최신 항목으로 찾습니다.
  - 결과: 1개면 사용합니다. 2개 이상이면 번호를 붙인 후보 목록으로 묻습니다(다음 턴의 "첫 번째", "내일 거"는 Python이 후보 안에서만 해석). 0개면 "찾지 못했어요"와 그날 일정 목록을 보여 줍니다. 없는 일정을 바꿨다고 처리하지 않습니다.
- **충돌 검사** `find_conflicts(start, end, exclude_id)`
  - 반열린 구간 `[start, end)`로 비교합니다. `a.start < b.end and b.start < a.end`이면 충돌입니다.
  - `scheduled`인 일정만 비교합니다. 날짜가 붙은 시각으로 비교하므로 자정을 넘는 일정도 그대로 맞게 계산됩니다.
  - 일정을 옮길 때는 원래 소요 시간(`end - start`)을 유지합니다.
- **변경 제한 일정 보호**
  - 대상 일정이 `reschedulable=false`이면 변경·취소 제안을 만들지 않고 이유를 안내합니다.
  - 충돌 상대가 보호된 일정이어도 그 일정을 옮기지 않습니다. 후보만 찾습니다.
- **사용자가 직접 말한 시각**: 자동 추천 범위(07~21시)와 관계없이 검사합니다. 막는 경우는 세 가지뿐입니다.
  - 지난 시각
  - 충돌 (대안을 안내함)
  - 보호 일정
  - 이른 새벽·늦은 밤 시각은 막지 않고, 승인 카드에 "늦은 시각이에요"라는 표시만 붙입니다.
- **자동 후보 탐색** `find_free_slots(day, duration, prefer_at, now, window=AUTO_WINDOW)`
  - 사용자가 시간 선택을 맡겼거나, 원하는 시각이 충돌할 때만 씁니다.
  - 기본 범위는 07:00~21:00이고 30분 간격으로 봅니다. 이 범위는 프로젝트 설정 상수이며 자동 추천에만 적용합니다.
  - 사용자가 "저녁쯤", "모레 오전"처럼 시간대를 말했다면 그 시간대 범위를 씁니다.
  - 고르는 조건: 지금 + 10분 이후, 충돌 없음, 원래 소요 시간 유지. 원하는 시각에 가까운 순, 같은 거리면 늦은 쪽 먼저. 최대 3개입니다.
  - 실외 일정은 후보별 예보 상태를 3가지로 나눠 표시합니다.
    - `good`: 조회했고 위험 신호가 없음
    - `bad`: 조회했고 `forecast_signals` 신호가 있음
    - `unknown`: 조회 실패, 16일 초과, 조회 상한
  - `unknown`인 후보를 "날씨가 좋다"는 근거로 추천하지 않습니다. "비 안 오는 시간"을 원했는데 모든 후보가 `bad`나 `unknown`이면, 추천하지 않고 그 사실을 알립니다.
  - 그날 빈 시간이 없으면 다른 날짜를 찾기 전에 먼저 묻습니다. 허락하면 최대 3일만 더 찾습니다.
- **완료 기록 조건**: 일정 상태별로 다르게 처리합니다.
  - `completed`: "이미 완료로 기록돼 있어요" (제안 없음)
  - `cancelled`: "취소된 일정이라 완료로 기록할 수 없어요" (제안 없음)
  - 진행 중이거나 시간이 지난 `scheduled`: 완료 제안
  - 오늘이지만 아직 시작 전: "예정 시각(오후 2시) 전인데 완료로 기록할까요?" 표시를 붙여 제안
  - 내일 이후 일정: 제안하지 않고 "아직 날짜가 오지 않은 일정이에요"라고 안내
- **상대 시간** `resolve_shift(shift_text, base)`
  - 기준(`schedule`/`now`)은 LLM이 고르고, 계산은 `datetime`/`timedelta`로 합니다.
  - 일정 기준 예: "미뤄·늦게·앞당겨·다음 날 같은 시간·일주일 뒤"
  - 지금 기준 예: "지금부터 9시간 뒤"
  - 기준이 `unknown`이고 대상 일정이 있으면 "원래 시간보다 두 시간 뒤인가요, 지금부터인가요?"라고 묻습니다.
- **날짜·시간 보강** (기존 함수 앞에서만 처리)
  - 한글 분("십오 분" → "15분")
  - "다음 달·이번 달 N일" (기존 함수는 "다음 달"을 무시함)
  - "일주일·N주 뒤"
  - 앞 대화 날짜를 기준으로 하는 "그날·다음 날"
  - 대략 표현("쯤·경·조금 넘어서·무렵")은 `approximate=True`로 표시하고, 승인 카드에 정확한 시각을 보여 줍니다.
  - 오전·오후가 불명확한 "네 시"·"세 시 반"은 기존 함수가 이미 되묻습니다.
  - "아침 일찍"·"저녁쯤"은 시간대 범위 안에서 빈 시간을 찾습니다.

## 6. 일정 이해 LLM 호출과 의도 분류 보완
**3단계 수정** (`outing_decision.py`, 가능한 한 작게)
1. `INTENTS`에 `schedule_query`(조회·다음 일정·남은 일정·생활 기록 요약), `schedule_create`, `schedule_cancel`, `schedule_complete`, `schedule_history`를 추가합니다.
   - 기존 `schedule_change`는 이름을 그대로 둡니다. `ROUTES`는 계속 `INTENTS`에서 만들어지므로 A 계약 테스트가 그대로 성립합니다.
2. `UNDERSTANDING_PROMPT`에 새 의도의 정의와 예시를 넣습니다. 실패했던 문장 "…비 오면 시간 바꿀까?"를 `schedule_change` 예시로 넣고, 생활 지원(우유·계란)과 구분하는 예시도 넣습니다.
3. `run_outing_decision(..., schedule_hint=None, schedule_handoff=False)`: 기본값이 있는 키워드 인자이므로 기존 호출은 그대로 동작합니다.
   - `schedule_hint`: 등록된 일정 제목·날짜 최대 8개를 이해 단계 자료에 넣습니다.
   - 새 일정 의도이거나 (`schedule_handoff=True`이고 `schedule_change`)이면 날씨·RAG·답변 LLM을 건너뜁니다. 이때 `route=의도`, `decision.kind="schedule_handoff"`, `answer_source="handoff"`로 돌려줍니다. LLM 호출은 1회입니다.
4. **변경 동사는 의도를 확정하지 않습니다** (v1의 보정 규칙 삭제)
   - 3단계는 모델이 고른 의도를 그대로 둡니다.
   - 저장소가 연결돼 있고, 모델이 `weather_question`·`outing_consultation`으로 분류했는데 발화에 일정·시간 표현과 변경 동사가 함께 있으면, 그래프가 일정 이해 LLM에 **한 번 더 판단**을 맡깁니다(재확인 넘김, `turn_hops` 1회).
   - 일정 이해 결과가 `operation=other`이거나 `request_mode`가 부정·질문이면, 원래 3단계 결과로 돌아가 답합니다. 3단계 답변은 이미 만들어져 있어 다시 호출하지 않습니다.
   - 모델이 처음 고른 의도, 재확인 결과, 최종 경로를 모두 기록합니다. 그래서 모델 성능과 그래프 보정 효과를 따로 보고할 수 있습니다.

**일정 이해 호출** (`schedule_agent.py`, 1회, 온도 0, JSON 스키마)
- 필드
  - `operation`: query, create, update, cancel, complete, other
  - `query_scope`: date, target, next, remaining, week, history, summary, none
  - `answers_previous_question`
  - `target_ids`: 이번 호출에 넘긴 일정 id만 고를 수 있도록 스키마에서 제한합니다
  - 문자열: `target_text`, `date_text`, `time_text`, `new_date_text`, `new_time_text`, `shift_text`, `duration_text`, `title`, `city_text`, `reason_text`
  - `shift_base`: schedule, now, unknown
  - 참·거짓: `delegate_choice`, `other_day_ok`, `check_weather`, `multiple_requests`
  - `preferences`: avoid_rain, avoid_heat, avoid_cold, avoid_wind
  - `category_guess`
  - (v2 추가) `request_mode`: request(요청), negated(부정·불필요: "바꾸지 마", "바꿀 필요 없어", "원래 시간에 갈래"), conditional(조건부: "비가 오면 바꿀까?"), question(묻기만 함), correction(정정: "~말고 다른 일정", "일곱 시 아니고 여덟 시")
  - (v2 추가) `exclude_previous_target`, `corrects_field`: date·time·target·none
- 텍스트 필드는 사용자 발화(이번 발화와 직전 발화)에 실제로 있어야 합니다. 없으면 버립니다. 3단계 `ground_slots`와 같은 방식입니다.
- 일정 상담이 진행 중이면 다음 턴은 이 호출 하나만 합니다. 결과가 `operation=other`(날씨·생활 지원 등)이면 a_node로 한 번 넘깁니다. 생활 지원이면 a_node 다음에 기존처럼 b_node로 갑니다.

**`request_mode`별 처리** (Python)
| 모드 | 처리 |
|---|---|
| request | 정상 흐름 (대상 → 시각 → 충돌 → 제안) |
| negated | 제안을 만들지 않고 초안을 비웁니다. "원래 일정(오후 2시)을 그대로 둘게요" |
| conditional | 조건(비 등)에 해당하는 예보를 실제로 조회합니다. 조건이 맞으면 변경을 제안합니다. 안 맞으면 "예보상 비 신호가 없어 그대로 두셔도 될 것 같아요"라고 하고 제안하지 않습니다. 조회하지 못하면 확인 불가로 안내합니다 |
| question | 조회 답변만 합니다 |
| correction | 바뀐 항목만 갱신합니다. "다른 일정"이면 직전 대상 id를 후보에서 빼고 다시 묻습니다. "일곱 시 아니고 여덟 시"처럼 시각을 정정하면, 직전 초안의 오전·오후(저녁 → 오후)를 이어받아 계산하고 그 사실을 표시합니다. 이어받을 근거가 없으면 되묻습니다 |

**대상 일정 채택 규칙**: LLM이 고른 `target_ids`만으로는 채택하지 않습니다. 아래 근거 중 하나가 있어야 합니다.
- 발화에 근거가 있는 `target_text`가 그 일정의 제목·별칭과 맞음
- 사용자가 말한 날짜·시각·시간대가 그 일정과 맞음
- 직전 질문의 후보 목록에서 사용자가 번호·날짜로 고름
- 근거가 없으면 "시장 장보기 일정 말씀이신가요?"라고 확인 질문을 합니다

**v2 테스트 문장 8개** (M: 가짜 LLM으로 처리 경로 확인 / L: 실제 모델의 `request_mode` 정확도 측정)
- "내일 일정을 바꿔 줘." → 대상이 여러 개면 묻기, 1개면 새 시각 묻기
- "내일 일정 바꾸지 마." → 제안 없음
- "시간을 바꿀 필요는 없어." → 제안 없음
- "비가 오면 시간을 바꿀까?" → 조건부: 예보 조회 후 판단
- "아니, 원래 시간에 갈래." → 초안 폐기, 제안 없음
- "아까 말한 일정 말고 다른 일정이야." → 직전 대상 제외하고 다시 묻기
- "저녁 일곱 시 아니고 여덟 시야." → 20:00으로 다시 계산
- 일정 상담 도중 "오늘 날씨 어때?" / "우유가 떨어졌어" → a_node(날씨) / b_node로 넘김, 일정 초안은 보존

**LLM과 Python의 책임 분리**
| LLM이 하는 일 | Python이 하는 일 |
|---|---|
| 의도 분류, 사용자 표현 옮겨 적기, 대상 일정 의미 매칭(`target_ids`), 상대 기준 판단, 시간 선택을 맡겼는지 판단, 후보 중 선택과 이유 코드(위임 시) | 날짜·시각 계산, 대상 일정 존재 확인, 충돌·보호·빈 시간, 예보 조회와 수치 비교, 제안 봉투, 저장 전 재검사, 저장, 안내 문장의 사실 부분 |

- **시간 선택을 맡긴 경우**(요구 15)
  1. Python이 후보를 최대 3개 계산하고, 후보별 예보를 조회합니다. 원래 시각을 포함해 최대 4구간입니다.
  2. LLM이 `{"choice": "C1"|"C2"|"C3"|"none", "reasons": [less_rain, lower_wind, milder_temp, no_conflict, closer_to_original]}`를 고릅니다.
  3. Python이 그 이유가 실제 수치와 맞는지 확인하고 문장으로 만듭니다.
  4. 맞지 않거나 호출이 실패하면 Python 규칙으로 고르고 `answer_source="python_fallback"`으로 표시합니다.
  - 좋은 후보가 없으면(모든 후보에 비 신호가 있음) 억지로 추천하지 않습니다. "비가 오지 않는다"고 보장하지도 않습니다.
- 안내 문장은 Python 틀로 만듭니다. 일정 이름, 이전·이후 시각("오후 5시"), 충돌 여부, `[확인한 예보]`, 공식 수칙 원문을 넣습니다. 이렇게 하면 지어낸 날씨·일정이 생길 수 없습니다.
- 모델 JSON이 잘못되면 1회 다시 요청합니다. 그래도 실패하면 `llm_invalid_output`, Ollama가 꺼져 있으면 `llm_unavailable`로 알립니다. 날짜·시간이 분명한 단순 조회도 LLM 없이 처리하지 않습니다(의도는 LLM이 판단).

## 7. LangGraph 확장 구조
```text
START → intake ─┬─ 입력 오류·상담 끝내기 ──────────────→ END
                ├─ active_feature=="B" ───────────────→ b_node   (기존 그대로)
                ├─ active_feature=="S" (일정 질문 중) ──→ schedule_node
                └─ 그 밖 ──────────────────────────────→ a_node
a_node ─┬─ A 제안 → (저장소 연결 시 저장된 일정과 연결, 10절) → approval / 되묻기·신규 등록 제안
        ├─ living_support → b_node
        ├─ 일정 의도 → schedule_node
        ├─ 날씨·외출 상담인데 일정+변경 동사 (재확인, hops 0) → schedule_node
        └─ END
schedule_node ─┬─ 제안 → approval   ├─ operation=other & 이번 턴 넘김 0회 → a_node
               └─ 조회 답변·추가 질문(active="S") → END
approval → execute(승인) / close(거절·취소) / approval(무시)   ← 기존 그대로
```
- State 추가 필드: `schedule_conversation_state`(일정 대화 전용), `turn_hops`(턴당 노드 간 넘김 횟수, `intake`가 0으로 초기화, 상한 1). `active_feature`에 `"S"` 값을 추가합니다.
- `build_graph(..., schedule_store=None, schedule_runner=None, life_record_reader=None)`
  - **(v2) `schedule_store=None`이면 `schedule_node`를 추가하지 않습니다.** 노드 6개와 분기 대상 목록이 4단계와 같아서 G1(노드 6개 정확히 비교)이 바뀌지 않습니다.
  - 저장소 미연결 상태에서 3단계가 새 일정 의도를 돌려주면 `a_node`가 "일정 관리 기능이 연결되지 않았어요"라고 안내하고 끝냅니다. 그래프 구조는 그대로입니다.
  - 저장소를 연결한 그래프(노드 7개)는 `test_schedule.py`에서 따로 검증합니다.
  - 추가 회귀 테스트: 저장소 미연결 그래프의 Mermaid가 5단계 이전과 같은지 비교합니다.
- 저장소를 연결하면 `a_node`는 `run_outing_decision(..., schedule_hint=저장소 요약, schedule_handoff=True)`로 호출합니다.
- '그만·취소·처음으로'만 단독으로 말하거나 '상담 끝내기' 버튼을 누르면 S 상담도 끝냅니다(B와 같은 규칙). "내일 장보기 취소해 줘"처럼 문장이면 일정 취소 요청으로 처리합니다.
- **실행 뒤 동기화**(9.4)
  - 일정 작업이 성공하면 `schedule_conversation_state`의 초안을 비웁니다.
  - `a_conversation_state`를 초기화합니다(기록: `a_state_reset_after_schedule_change`). 이전 외출 대화의 14시 정보나 예보 캐시를 다시 쓰지 않게 하기 위함입니다.
  - 이후 질문은 항상 저장소를 다시 읽어 답합니다.

## 8. 새 승인 데이터
- `ALLOWED_ACTIONS`에 추가하는 type 4개: `create_schedule`, `update_schedule`, `cancel_schedule`, `complete_schedule`
  - 모두 source `schedule_service`, feature `S`, 실행 함수는 `schedule_executor`입니다.
  - 기존 `propose_outing_time_change`(A)와 `request_caregiver_help`(B)는 그대로 둡니다.

{"schedule_id": "schedule_001|null(등록)", "expected_version": 1,
 "before": {"title","start_at","end_at","status"} | null, "after": {...} | null,

  - 변경 거절: "원래 일정(오후 2시)을 그대로 둘게요" + 공식 수칙 한 줄
  - 등록 거절: "등록하지 않았어요"
  - 취소 거절: "취소하지 않고 그대로 둘게요"
  - 완료 거절: "완료로 기록하지 않았어요"

## 9. 저장·중복 실행 방지 (`schedule_store.py`)
- **잠금**
  - 같은 프로세스 안: 경로별 `threading.Lock`
  - 다른 프로세스: `store.json.lock` 파일을 `os.O_CREAT|O_EXCL`로 만듭니다. 파일 안에는 만든 시각과 프로세스 번호만 적습니다(개인정보 없음). 5초 동안 다시 시도한 뒤 실패하면 `lock_timeout`
  - **(v2) 비정상 종료로 남은 잠금 파일**
    - 만든 지 30초가 넘은 잠금 파일은 버려진 것으로 봅니다. 한 번의 읽기·쓰기는 수 밀리초면 끝나기 때문입니다.
    - 이때 잠금 파일을 `*.lock.stale-<시각>`으로 이름을 바꾸고, 경고를 `tool_trace`에 남긴 뒤 진행합니다.
    - Windows에서 `os.kill(pid, 0)`은 프로세스를 종료시킬 수 있으므로 프로세스 생존 확인에는 쓰지 않습니다. 시각 기준만 씁니다.
    - 잠금 실패·`lock_timeout`일 때는 아무것도 쓰지 않으므로 기존 데이터가 그대로 남습니다.
  - **보장 범위 (문서화)**
    - 같은 프로세스의 스레드: 보장
    - 다른 프로세스: 잠금 파일 방식의 최선 노력. 한 프로세스가 30초 넘게 잠금을 쥐는 비정상 상황은 보장하지 않습니다.
    - 네트워크 드라이브·Google Drive 동기화 폴더는 보장 범위 밖입니다.
- **원자적 저장**: 같은 폴더에 임시 파일 작성 → `flush`·`fsync` → `os.replace`. Windows에서 `PermissionError`가 나면 짧게 3번 다시 시도하고, 그래도 실패하면 `write_failed`로 알립니다. 원본 파일은 그대로 남습니다.
- **오류 처리**: 아래 경우는 `ScheduleStoreError(code)`를 냅니다. **파일을 초기화하거나 덮어쓰지 않습니다.** 사용자에게는 "일정 파일을 읽지 못했어요"라고 안내합니다.
  - 파일 없음(초기화 이후), 잘못된 JSON, 스키마 오류, 읽기·쓰기 권한 없음
- **(v2) 최초 생성만 허용**
  - `ensure_initialized(now)`는 저장소 파일과 `schedule_store.created` 표시 파일이 **둘 다 없을 때만** 초기 데이터로 만들고, 표시 파일을 남깁니다(`store_id`·생성 시각).
  - 표시 파일은 있는데 저장소가 없거나 손상됐으면 다시 만들지 않습니다. `store_missing`·`corrupt` 오류로 알리고 복구 방법(백업 파일 복원, 또는 사용자가 직접 두 파일을 지우고 다시 초기화)을 안내합니다.
  - 파일이 있으면 절대 덮어쓰지 않습니다.
- **(v2) 테스트 격리**
  - 모든 테스트는 `TemporaryDirectory` 경로를 직접 넘기고, 환경변수 `SAFEMATE_SCHEDULE_PATH`도 비운 상태로 실행합니다.
  - 테스트 전후에 운영 경로 `.safemate/schedule_store.json`의 존재 여부와 해시가 같은지 비교합니다.
- **멱등성**: `action_history`에 `action_id`와 `content_hash`(type·payload 기준)를 남깁니다.
  - 같은 id·같은 내용이 다시 오면 `already_executed`와 기존 기록을 돌려줍니다. 프로그램을 다시 실행해도 같습니다.
  - 같은 id인데 내용이 다르면 `invalid_action`(`action_id_reused`)으로 거절합니다.
- **일관성**: 일정과 이력을 한 JSON 문서에 함께 쓰고, 한 번의 `os.replace`로 저장합니다. 그래서 일정과 이력이 서로 어긋날 수 없습니다.

## 10. 저장 직전 재검사와 실행 결과
`apply_schedule_action(approved, store)`는 잠금을 잡은 채로 다시 읽고, 아래 순서로 확인합니다. 하나라도 실패하면 저장하지 않습니다.
1. 그래프가 붙인 `approval.status=="approved"`, type·source·`action_id` 형식
2. 멱등성(9절)
3. 대상 일정이 존재하는가, `version == expected_version`인가, `before`(시작·끝·상태)가 지금 값과 같은가 → 다르면 `stale`
4. 보호 일정인데 변경·취소인가 → `protected`
5. 새 시각과 지금 저장된 일정의 충돌 → `conflict`
6. 지난 시각으로 등록·변경하는가 → `invalid_action`
7. 저장: `version`+1, `updated_at`, 상태·완료 시각 갱신, 이력 추가

반환 형식은 2.3·3.7 계약과 같습니다: `{status, message, action_id, applied, mock: true, record, answer}`.
- `stale`·`conflict`·`protected`·`not_found`일 때는 "승인 대기 중에 일정이 바뀌어 저장하지 않았어요. 다시 확인해 주세요."처럼 실행 함수가 만든 안내를 보여 줍니다. 이 경우에도 그래프는 성공으로 판정하지 않습니다(`applied=False`).
  - 이 예외는 S type에만 적용합니다. 그래서 기존 G12 테스트(`status=error` 등)의 "실패 문장" 동작은 그대로입니다.
**(v2) 기존 A 제안(`propose_outing_time_change`)을 저장소와 연결**: 실행 단계가 아니라 **승인 카드를 만들기 전에** `a_node`에서 처리합니다.
- 저장소가 연결된 상태에서 A가 제안을 돌려주면(날씨 기반 외출 상담), `a_node`는 봉투로 감싸기 전에 `link_outing_proposal(store, a_result, now)`를 부릅니다.
  1. 대상 후보: A의 `outing_request`(날짜·출발 시각·지역·목적)로 `scheduled` 일정을 찾습니다.
     - 날짜가 같아야 합니다.
     - 원래 출발 시각이 일정 구간 `[start, end)` 안에 있거나 시작과 같아야 합니다.
     - 지역이 있으면 같아야 합니다.
     - 목적이 있으면 제목·별칭과 맞아야 합니다. **시작 시각 하나만으로는 연결하지 않습니다.**
  2. 정확히 1개: `update_schedule` 봉투를 만듭니다.
     - `schedule_id`, `expected_version`, `before`(그 시점의 일정 전체)를 넣습니다.
     - 원래 소요 시간을 유지한 새 구간을 계산하고, 충돌·보호를 검사합니다. 충돌하면 승인 카드를 만들지 않고 대안을 안내합니다.
     - A의 예보 비교 이유와 `[확인한 예보]`를 `payload.reason`·`weather_lines`에 옮깁니다.
  3. 여러 개: 승인 카드 없이 후보 목록으로 묻습니다. `schedule_conversation_state`에 대상 고르기 초안(새 시각 포함)을 저장하고 `active="S"`로 둡니다.
  4. 0개(저장되지 않은 외출): 기존 일정을 고치지 않습니다. 사용자가 말한 목적·지역과 제안 시각으로 `create_schedule` 봉투를 제안합니다. 카드 문구는 "새 일정으로 등록할까요?"이고 소요 시간 기본값 60분을 표시합니다. 제목이 없으면 묻습니다.
- 저장 직전에는 10절의 1~7을 똑같이 다시 검증합니다.
- `apply_outing_change(approved, store)`(명세 3.7 호환 이름)
  - 4단계 계약대로 `a_executor`로 꽂을 수 있게 남겨 둡니다.
  - `payload`에 `schedule_id`·`expected_version`·`before`가 없는 옛 봉투는 **저장하지 않고** `invalid_action`("대상 일정을 확인하지 않은 제안")으로 거절합니다.
  - 저장소 연결 모드에서는 위 연결 과정 때문에 옛 봉투가 승인 단계까지 가지 않습니다.

## 11. 장치 자동 선택 (`device_utils.py`)
- `select_embedding_device(requested="auto") -> {"selected", "mode", "attempts":[{device, stage, ok, reason}], "details"}`
  - `auto`: cuda → xpu → cpu 순서로 시도합니다. 장치마다 두 단계를 거칩니다.
    1. 기존 `configure_embedding_device()`: `is_available` + 텐서 연산
    2. **(v2)** 기존 `load_embeddings()`: 실제 MiniLM 로딩 + `verify_embedding_device` 확인(가중치·토큰 입출력·출력 장치, 384차원)
    - 둘 다 성공한 첫 장치를 고릅니다. 실패하면 장치·단계·이유를 기록하고 다음 장치로 넘어갑니다.
    - `load_embeddings`는 `lru_cache`라서, 고른 장치의 모델은 이후 RAG 색인 준비에서 그대로 다시 씁니다.
  - 명시 지정(`cuda`·`xpu`·`cpu`): 같은 두 단계를 거치고, 실패하면 다른 장치로 바꾸지 않고 오류를 냅니다.
- **(v2) 실제 실행 경로에 연결**
  - `build_graph(a_device="auto")`(그리고 `b_device`도 지정 가능)이면 그래프를 만들 때 `select_embedding_device`를 **한 번** 실행합니다. 고른 장치 문자열을 A 일정·RAG 호출에 넘기고, 선택 결과를 `graph_info`(앱 함수 `runtime_report()`)로 볼 수 있게 남깁니다.
  - 3단계 CLI `--device`에 `auto` 선택지를 추가합니다. 인자 처리 한 줄이며, 기존 `xpu`·`cuda`·`cpu` 동작은 그대로입니다.
  - 요청마다 장치를 다시 고르거나 환경변수를 바꾸지 않습니다. A·B 장치·색인은 각각 따로 유지합니다.
- `ollama_report()`: 기존 `od.ollama_status()`의 `/api/ps` 결과를 3가지로 구분합니다.
  - 모델이 메모리에 없음 → "Ollama 모델이 아직 메모리에 올라가지 않아 실행 장치를 확인할 수 없음" (**CPU라고 쓰지 않음**)
  - 올라갔고 `size_vram`이 0 → "CPU 메모리에서 실행 중"
  - 올라갔고 `size_vram`이 0보다 큼 → "GPU 메모리 사용(비율)"
  - PyTorch 장치와 별도 항목으로 보고합니다. 실제 실행(L층) 직후에 다시 조회해서 보고합니다.
- `python device_utils.py --device auto|cuda|xpu|cpu`로 보고서를 출력합니다. 테스트 파일도 `--device auto`를 받습니다. 패키지는 설치하거나 바꾸지 않습니다.
- **(v2) Colab 안내 (README)**
  - `/content`는 세션이 끝나면 지워집니다. 일정을 계속 보관하려면 Google Drive를 연결하고 `SAFEMATE_SCHEDULE_PATH=/content/drive/MyDrive/safemate/schedule_store.json`처럼 지정해야 합니다.
  - Drive 동기화 폴더에서 여러 프로세스가 동시에 쓰는 것은 보장 범위 밖입니다.
  - Ollama는 Colab에 별도로 설치하고 서버를 실행해야 합니다(수업 4장 세팅).
- 경로는 `pathlib`과 `Path(__file__).parent` 기준으로 만듭니다. 환경변수 `SAFEMATE_SCHEDULE_PATH`로 바꿀 수 있습니다. JSON은 UTF-8, 시각은 모두 KST입니다.
- **학교 GPU 서버와 Colab에서 확인할 명령**
  - `python device_utils.py --device auto` → `selected=cuda`와 실제 임베딩 장치 `cuda:0` 확인
  - `python test_schedule.py --device cuda`
  - `python test_safemate_graph.py --live-ollama --device cuda`
  - 설치 조건: CUDA용 PyTorch 빌드(서버 드라이버에 맞는 `cu12x` 인덱스), Colab은 기본 설치 사용
  - 이번 PC에서는 CUDA를 가짜 `torch`로만 검증합니다. 실제 검증 완료로 보고하지 않습니다.

## 12. B기능 인터페이스 호환성
- `b_node`, `run_living_support()`·`execute_living_action()` 호출 모양, B 봉투 검사, `approval` 규칙, B 거절 문장은 **바꾸지 않습니다.** 명세 2장도 수정하지 않습니다.
- 새 type 이름은 `request_caregiver_help`와 겹치지 않습니다. S 검사는 별도 분기입니다.
- 생활 기록 통합 조회: `life_record_reader`의 기본값은 `None`입니다. 이때 "보호자 도움 요청 기록은 생활 지원 기능이 연결되지 않아 확인할 수 없어요"라고 안내합니다.
  - 명세 2.3의 JSONL 형식(`action_id`·`type`·`payload.message`·`approved_at`·`executed_at`)을 읽는 어댑터 `read_living_action_log(path)`를 만들어 테스트합니다.
  - B가 연결된 뒤에만 이 어댑터를 주입합니다. 가짜 요청 기록은 만들지 않습니다.
- 회귀 확인: G7(B 흐름)·G8(상태 분리)을 다시 실행하고, 저장소를 연결했을 때 "우유하고 계란이 떨어졌어"가 B로 가는지 테스트합니다.

2. "시장 가는 시간 좀 바꿔 줘" → 새 시각 질문
